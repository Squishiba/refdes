Diagnostics (why it happens):
- parse.py `_apply_change_override` (the #228 mapping validation) only
  validates `fields:` when `isinstance(fields, dict)` (parse.py:1057); a
  non-dict `fields:` passes validation untouched and lands in
  `item.on_change_override`, where model.py:674
  `(self.on_change_override or {}).get("fields", {}).get(field_name)`
  crashes for list/str/int, and for null because the key exists with value
  None so the `.get("fields", {})` default never applies (`None.get`).
- Same non-dict list also crashes `refdes audit` (cli.py:1686
  `.items()`), i.e. it's not hash-only once it survives the load.
- F15: the loop validates each entry's MODE but never the field NAME; an
  entry naming an undeclared field is silently inert (on_change_for is only
  ever asked for declared fields + "body").

Convention decision for F15 (task: warning vs error — follow the existing
convention): the rest of on_change validation treats unknown NAMES as
ERRORS — parse.py:1079 `on_change: unknown key ...` is project.error, as
are all invalid mode values (parse.py:1049, 1070, 1024) and the
configcheck project-level checks (configcheck.py `self.keys(...)` →
SchemaError). The only warn in the area is the missing-`reason:` advisory
(parse.py:1093), which is a style nudge, not an unknown name. So F15 is
implemented as an ERROR, matching the unknown-key convention, with the entry
dropped (same "bad entry is dropped" posture as invalid modes).

B8 fix (parse.py `_apply_change_override`): a `fields:` key present with a
non-mapping value is now a clean load diagnostic naming file, line, item,
the received value, and the expected shape; the entry is dropped so the
rest of the override (mode:, reason:) still works and every command runs.
Covers list, string, number and null with the one shape check.
Note (not changed, out of scope): `on_change:` itself as a top-level list
is silently ignored (no crash) — pre-existing, untouched.

F15 fix (parse.py): `_apply_change_override` now takes the item's ItemType
`spec`; each `fields:` entry naming something outside `spec.fields` (plus
the special `body` name, which build.py:1949 feeds to on_change_for) errors
with the declared-field list and is dropped.

Tests: tests/test_change_policy_on_change_key.py
- B8: four shapes (list, string, number, null) each give exactly one clean

  behaviour is unaffected.
- F15: undeclared name → clean load, error naming the field and the type's
