## 2. The two doc lines at issue

docs/cli-reference.md:604-611 (the Citations-section paragraph), verbatim:

> Each citation line is `<state>  <pin>  cited by <items>`. **`state`** is what
> verification found — `ok`, `unpinned`, `cache_missing`, `hash_mismatch` or
> `missing` (see [citing a datasheet](markdown.md#citing-a-datasheet) for what
> each costs). **`pin`** says what the lockfile holds for that path: `no pin`
> (never fetched, so nothing is pinned), `hash-only` (pinned by `sha256`, no
> local copy — the default, since datasheets are generally copyrighted) or
> `kept` (pinned, with the bytes kept at `.refdes/copies/<sha256><ext>`). The
> two columns are independent facts about the same pin, so they never
> contradict each other: an unpinned citation has no hash to be `hash-only`
> about, and says `no pin`.

## 3. Where each column comes from

- state: `citations._resolve` (src/refdes/citations.py:995-1001) sets
  `state = "cache_missing"` when the lockfile says `kept_copy: true` but
  `kept_copy_path(...)` is not a file, and returns. That is the only place
  `cache_missing` is ever set.
- pin: `cli.cmd_audit` (src/refdes/cli.py:992-1006) — `if state == "unpinned":
  pin = "no pin"`, `elif any(s.kept_copy for s in statuses): pin = "kept"`,
  `else: "hash-only"`. The `kept` branch reads only the lockfile flag
  (`CitationStatus.kept_copy`, set at citations.py:992 from
  `record.get("kept_copy")`), never the filesystem.
- release gate: `lifecycle._rule_missing_kept_copies` (src/refdes/lifecycle.py:577)
  filters `status.state == "cache_missing"` — the state column's data, not the
  pin column's. So changing the pin word cannot touch it.

## 4. Which side is wrong — the code

The docs' claim is the *more* useful of the two, and the cheaper fix: one
`elif` in `cmd_audit`. Rewriting the doc instead would mean blessing a line
where the tool says a kept copy is kept and it is not — and the report is
right that a user reads that sentence and relies on it. So the pin column is
what changed.

`kept` is defined everywhere else in this project as *the bytes are kept at
`.refdes/copies/<sha256><ext>`* — docs/markdown.md:471-478, docs/output.md's
`kept_copy` table, `refdes fetch`'s own `kept` line (cli.py:755), which means
the write actually happened. Printing it when the file is not there makes the
word mean two things, and the wrong one is the one a release depends on.

Neither of the existing pin words fits, and that is the reason a fourth is
needed rather than a reuse:

- `hash-only` means *pinned by sha256 with no kept copy* — a mode the author
  chose and the lockfile records honestly (`kept_copy: false`). Here the
  lockfile says `kept_copy: true`. Printing `hash-only` would hide the fact
  that this project's decision was to keep the bytes and the bytes are gone,
  which is precisely the thing the release gate blocks on.
- `no pin` means nothing is pinned, no hash at all. Flatly false here.

So: `state == "cache_missing"` → pin reads `no copy`. One line now tells the
whole truth (`cache_missing  no copy  cited by CMP-PWR-001`) instead of needing
the docs to explain which of the two columns to believe.

**State column untouched, deliberately.** `missing_kept_copies` filters
`status.state == "cache_missing"` (lifecycle.py:577-585) — a different datum
from the pin word, so the change cannot reach it, but that is exactly the kind
of thing to pin with a test rather than reason about (below). Verified live too
(§5).

**`hash_mismatch  kept` left alone on purpose.** The blob *is* on disk there;
`kept` is true of it, and the state column is what says its bytes are wrong.
The two agree, so there is nothing to fix. Same reasoning would not apply to
`cache_missing`, where the file is absent.
