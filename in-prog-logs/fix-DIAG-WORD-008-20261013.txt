## The finding, confirmed before touching code

model.py `DESTINATION_REFUSAL` hard-codes `(read-only tree?)` and ids.py
caught bare `except OSError` at the write-back (HEAD :649) and the ledger
save (:696), so any filesystem failure — ENOSPC, EIO, ENAMETOOLONG — was
reported as a probable read-only tree, on a tree that was fully writable.
Reproduced first with fault injection (probe `.scratch/dw008/`):
hardware@3 project + `enospc_run.py` monkeypatching
`refdes.textio.atomic_write_text` to raise `OSError(errno.ENOSPC, ...)`
for writes to r.yaml/ids.yaml, then `cli.main(["id"])`:

    ERROR items/r.yaml:3 — cannot write items/r.yaml (read-only tree?) -- ...
    ERROR <project> — cannot write .refdes/ids.yaml (read-only tree?) -- ...
    STATUS 1 / TREE_WRITABLE True True

`os.access` confirmed both dirs writable during the run, so the printed
hint was false. This contradicts docs/cli-reference.md's own stated
principle (:106-113): for writes that "can be refused for reasons that
have nothing to do with a read-only tree ... the marker would be a claim
refdes cannot make there" — the reason build's site refusal and keys
adopt/restore already report the OS's own reason.

## The fix

- model.py: new `could_be_read_only(exc)` — True for `PermissionError`
  (including textio's own read-only guards, which raise it with no errno —
  that's why the predicate checks the type, not just errno 13, which would
  also have broken root/Windows CI) and for EACCES/EPERM/EROFS
  (`READ_ONLY_ERRNOS`). New `write_refusal_reason(exc)` follows the
  existing `strerror`-or-bare-errno convention already used by
  sources.py:440, citations.py:2291, cli.py:423.
- `destination_refusal(path, consequence, cause=None)`: with `cause`, the
  parenthetical becomes the OS's own reason when `could_be_read_only` is
  False; byte-identical `(read-only tree?)` otherwise, including every
  call site that passes no cause.
- ids.py: both catches bind `exc`, pass it, and split the remedy sentence
  — "Make the tree writable / Make .refdes/ writable" only for failures
  that could be one; "Fix the reported failure ..." otherwise. Read-only
  output is byte-identical to before.

## Limitations / deliberately out of scope

- Scope was model.py/ids.py/tests. `history._store_refusal`, scaffold's
  two preset refusals, `revise._refuse_item_write` and `stub_tests` all
  catch `OSError as exc` and still call `destination_refusal` without the
  cause, so they keep the unconditional marker — same latent mis-blame,
  ready for a follow-up now that the helper accepts the cause.
- The load-time degrade (`READ_ONLY_REFUSAL`/`read_only_refusal`, the
  "(load could not write this file ...)" warning) is likewise untouched;
  the finding named only the destination shape.
- docs/cli-reference.md:102-105 says destination refusals "do all contain
  `(read-only tree?)`" — true for every failure that could be one, but
  under this fix a non-permission refusal reports the OS reason instead.
  The docs sentence now needs a qualifier; left for the docs follow-up
  because docs were out of the stated scope.
