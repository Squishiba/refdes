## Commit 2 — `refdes revise` silently ignores an `ids:` mapping

### Reproduced

.scratch/rv1 is a clean `base` with keys minted (one writable load), handed a
mapping file holding an `ids:` section:

    ids:
      REQ-PWR-001: REQ-PWR-011

    $ refdes revise rename.yaml
    nothing to do -- mapping doesn't apply to this project
    [exit=0]

Nothing was renamed and exit 0 says the mapping was fine. That is the worst
shape a silent no-op can take: a user who thought `revise` could rename one
item is told the file didn't apply, not that the section wasn't read.

### What `revise` actually accepts, and where the gap is

- `refdes revise --help`: "path to a YAML file with types:/fields:/links:/prefixes:
  renames" — which is already **four** of the five sections, and it omits
  `citation_keys:` (revise.py:74, documented in `mapping_from_dict`'s own
  docstring at revise.py:123, used by the bundled standard's own
  `migration.yaml`). So the help is wrong on its own terms before mine is
  considered.
- `mapping_from_dict` (revise.py:110-146) reads exactly five keys —
  `types`, `fields`, `links`, `prefixes`, `citation_keys` — via `.get(...)`
  with no check for anything else. That is the whole gap: an unknown
  top-level section is dropped on the floor, and if it is the *only* section
  then `Mapping.is_empty()` (revise.py:76) is True and the caller prints
  "nothing to do".

Read all five keys at revise.py:134-142 and the SchemaError shape at
revise.py:131-132.

### The refusal

Same message-adding shape as commit 1, same place in the file: one check in
`mapping_from_dict`, so it fires on **both** front doors and on
`--dry-run` for free (verified below — `load_mapping` is reached before
anything else looks at the Mapping). `revise.py` gains
`ACCEPTED_SECTIONS` and `_refuse_unknown_sections` at the top of the module,
next to `Mapping`; `mapping_from_dict` calls the check right after its own
non-dict check.

The accepted sections are named in the error, and `ids:` gets the one pointer
the brief asked for: single-item renames are done by editing `id:` by hand,
after a writable load has given the reference a key, which is Troubleshooting's
`### Hand-renaming an item is safe — get one writable load in first` section
(added by #126). Both halves verified by running them, not inferred — the
pointer says "after a writable `refdes check`" and not just "edit `id:` by
hand" because that is the half that matters:

- a hand-edited `id:` whose references are composites follows the rename on
  the next load, `0 errors`, exit 0 (the #126 trace, re-run here);
- while still bare it dangles, which is the error this whole commit is about.

The pointer is added **only when `ids` is among the unknown sections**, so a
typo'd `type:` gets the accepted list and nothing else.

    BEFORE (.scratch/rv1, `ids:\n  REQ-PWR-001: REQ-PWR-011`)

    $ refdes revise rename.yaml
    nothing to do -- mapping doesn't apply to this project
    [exit=0]
    $ grep -n "id: REQ-PWR-0" items/requirements.yaml     # unchanged
    3:    id: REQ-PWR-001
    9:    id: REQ-PWR-002
    14:    id: REQ-PWR-003
    19:    id: REQ-PWR-004

    $ refdes revise rename.yaml --dry-run
    nothing to do -- mapping doesn't apply to this project
    [exit=0]

    An arbitrary unknown section (`mystery:`) — same silent no-op.
    A *mixed* file (`prefixes: {REQ-PWR: NEED-PWR}` + `mystery:`) — printed
    the full prefix-rename plan, applied it, and dropped `mystery:` without a
    word. That is the worse of the two, and is why the check is a whitelist
    over *any* unknown key rather than a special case for `ids:`.

    AFTER (.scratch/rv2, same files)

    $ refdes revise rename.yaml
    error: rename.yaml: unknown top-level section 'ids'. A mapping file may have types:, fields:, links:, prefixes: or citation_keys:, and an unrecognised section is refused rather than ignored. To rename a single item, edit its `id:` by hand instead, after a writable `refdes check` has expanded references to composite form so they follow the rename -- see https://squishiba.github.io/refdes/troubleshooting.html#links.
    [exit=2]

    $ refdes revise rename.yaml --dry-run
    <byte-identical line>
    [exit=2]

    $ refdes revise other.yaml          # `mystery:` alone
    error: other.yaml: unknown top-level section 'mystery'. A mapping file may have types:, fields:, links:, prefixes: or citation_keys:, and an unrecognised section is refused rather than ignored.
    [exit=2]

    $ refdes revise mixed.yaml --dry-run   # prefixes: + mystery:
    error: mixed.yaml: unknown top-level section 'mystery'. ...
    [exit=2]

Nothing on disk moved in any of those; `REQ-PWR-001` is still `REQ-PWR-001`.
An all-accepted-but-empty mapping still prints `nothing to do` and exits 0 —
correct, nothing was asked for. A real `prefixes:` mapping still applies
(.scratch/rv3: 4 files changed, `REQ-PWR-001 -> NEED-PWR-001`, and the
subsequent check is `0 errors`, exit 0), so the guard costs the working case
nothing.

### Exit code

docs/cli-reference.md:13 — "`0` success, `1` errors found, `2` configuration
error (including `--no-write` refusal)". A mapping file with a section `revise`
doesn't implement is a bad input file, which is the same class as the missing
and unparseable mapping files that already exit 2 (revise.py's `load_mapping`
docstring calls an unreadable one "the configuration error it is", and
`cmd_revise`'s `except SchemaError` is the single exit). So the refusal raises
`SchemaError` rather than a project error, which is also what keeps it the one
exit for the whole module. Read the table rather than guessing the number.

### --dry-run

`revise rename.yaml --dry-run` on the same file: byte-identical error line,
exit 2, nothing written (above). It fires for free rather than by a second
check, because `load_mapping` runs before `apply()` is ever reached — so there
is no path where a dry run could report a plan for a mapping that a real run
would refuse.
