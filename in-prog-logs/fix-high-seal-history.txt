## SEAL-ORPHAN-001 (from PR #157, HIGH) — RE-CONFIRMED on d71c143, FIXED

Re-confirmation. Code unchanged from the report: `seal.py:624` was
`prefix = display_id.split("-", 1)[0]`. Reproduced with a real project via the
real CLI (`.scratch/probe_001.sh`, project under `.scratch/seal-orphan-*`):
types `log` (prefix `REQ-TMP`, append_only, sealing history after a
build-sealed first build) + `note` (prefix `NTE`, build-sealed); deleted
`REQ-TMP-002` after keys were written back:

- `refdes check` → exit 1, `ERROR REQ-TMP-002 — REQ-TMP-002 is append-only
  and was sealed, but no item with that id is in the project any more ...`
  (docs promise a legacy-seal WARNING).
- `refdes build --reseal` → exit 0 here (differing from the packet's exit 1 —
  the packet's project also had an NTE orphan; immaterial), printing BOTH
  `--reseal: sealing no longer applies to the 'log' type; nothing was
  rewritten` AND `REQ-TMP-002 was sealed as append-only ... dropping its
  seal; recorded in audit`.
- Seal file after: `reseals: [{action: remove, id: REQ-TMP-002, ...}]` and
  the record gone from `sealed:` — the silent record loss the docs say cannot
  happen.

Root cause: display ids are `prefix-number`, so a hyphenated declared prefix
(`REQ-TMP`) is truncated by `split("-", 1)[0]` to `REQ`, which matches no
declared `spec.prefix`; `candidates` falls back to *every* append-only type;
`all(... == history)` is False once a build-sealed append-only type exists —
even though the orphan provably came from the history-backed one.

Fix (`src/refdes/seal.py`, `_orphan_is_history_backed`): match the declared
prefix at a boundary (`display_id.startswith(f"{spec.prefix}-")`), longest
declaration first, instead of cutting at the first hyphen. The
no-match-falls-back-to-all conservatism is kept. Docstring updated to say so.

Verification by running: post-fix the same probe yields `check` exit 0 with
`WARNING REQ-TMP-002 — REQ-TMP-002 has a legacy seal record in
.refdes/log-seal.yaml ... The record is kept as it is.` and `--reseal` keeps
the record in `sealed:`.

Regression test: `tests/test_history_seal.py::test_a_hyphenated_prefix_still_
classifies_its_orphans` (hyphenated `REQ-TMP` history type beside build-sealed
`NTE`; asserts check warning at exit 0 and byte-identical seal file under
`--reseal`).
- Before fix (sabotage: reverted only the seal.py hunk): FAILED —
  `ERROR REQ-TMP-002 ... assert 1 == 0`, exit 1.
- After restoring fix: file passes, 25 passed.
Commands:
`PYTHONPATH=$PWD/src /home/jorb/work/venv-refdes/bin/python -m pytest tests/test_history_seal.py -q -p no:cacheprovider -k hyphenated`

## DOC-REMEDY-003 (from PR #168, HIGH) — RE-CONFIRMED on d71c143, FIXED

Re-confirmation. Code unchanged from the report at the named location
(now build.py:3145-3151 inside `warn_edited_after_captured`): the
`amends: [{label}]` sentence is emitted for every captured item. Reproduced
with the real CLI on a `standard: { base: hardware, version: 3 }` project
(`.scratch/probe_003.sh`, project under `.scratch/doc-remedy-*`). Note #176
merged `decision` into `log`, so the packet's `DEC-PWR-001` shape is no
longer a type — the over-reach is live for the remaining editable types,
reproduced with `requirement`:

- A: `refdes history capture REQ-001`, edit the body, `refdes check` → exit
  0, WARNING "… If the edit was a correction, revert it and append a new
  entry with `amends: [REQ-001]` instead …".
- B: doing what it says (log entry with `amends: [REQ-001]`) → exit 1,
  "ERROR items/log.md:2 [LOG-001] — amends may point at log, but REQ-001 is
  a requirement".
- C: contrast `amends: [LOG-001]` on a log → accepted, exit 0.

Root cause: F4's remedy encodes how an *append-only* entry is corrected, but
`warn_edited_after_captured` runs for any captured item (capture takes any
keyed item; `build()` calls the warning unconditionally), and `amends` in
hardware@3 is declared only on `log` with targets `[log]`
(standards/hardware/v3/base.yaml:294).

Fix (`src/refdes/build.py`): the `amends:` sentence is emitted only when the
item's type is append-only (the model the advice belongs to); an editable
type gets "The entry's type is editable, so a deliberate edit needs nothing
done about it; revert it if it was not deliberate." plus the same docs link.
Chose the report's own recommended gate ("gating on the item being of an
append-only type"). The stricter gate (some type declares `amends` targeting
this item's type) additionally suppresses the advice for append-only types
that never declare an `amends` verb — which changes behavior for
custom-schema projects (and PR-168's own fixture/pinned test), beyond what
the finding needs; noted as an option, not chosen.

Docs (step 4): `docs/troubleshooting.md` `## The design log` paragraph said
the warning always advises revert-and-`amends`; under the fix it does not
for editable types, so the paragraph was rewritten to describe both
branches. Both new remedy texts verified by actually running them:
- editable branch: probe_003.sh section A post-fix (REQ-001 warning).
- append-only branch: throwaway hardware@3 project, captured `LOG-001`
  edited → "If the edit was a correction, revert it and append a new entry
  with `amends: [LOG-001]` instead; otherwise there is nothing to do."
README's sample block (pre-F4 truncated quote) is the pr-168 MEDIUM
finding's stale-quote complaint, out of this HIGH finding's scope — left
alone.

Regression test:
`tests/test_history_edited.py::test_the_amends_remedy_is_offered_only_where_following_it_is_legal`
(schema with history-backed append-only `log` + editable `memo`; manual
`history capture` both; edit both; check: memo warning must NOT name
`amends`, log warning must still carry `amends: [LOG-001]`).
- Before fix (sabotage: reverted only the build.py hunk): FAILED — memo
