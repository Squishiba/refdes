## Root cause and where the fix belongs

serve/api.py `_create_preview` (:640) does `explicit = (query.get("id") or [""])[0] or None`
— empty collapses to None = auto. `_create_item` (:695 pre-fix) passed
`id=body.get("id")` straight into `edit.CreateRequest`, so `""` reached
`ids.plan_new_id` (explicit_id != None branch) and `split_id("")` refused it.

Chose to normalise at the HTTP boundary (api.py) rather than in ids.py or
edit.py: `plan_new_id`'s posture — explicit candidates are honoured verbatim
or refused as malformed, never renumbered — is asserted by
tests/test_ids.py::test_plan_new_id_explicit_override_is_honoured_or_refused
(a malformed explicit id is a refusal, not a re-plan), and the
"an empty HTTP string means the parameter was not given" convention is
already spelled at the route level for type/board/id/destination in the very
same module (and for destination again defensively in
edit._resolve_destination's `.strip()`). The service contract is
"id=None means next free" (CreateRequest docstring); "" was never a service
input, it is a wire artefact. So the POST route now does
`id=body.get("id") or None`, mirroring the preview route's `or None`. The
frontend (create.js) already omits an empty id from the body, so only raw
API clients hit this; the fix aligns the wire contract with the preview's.
