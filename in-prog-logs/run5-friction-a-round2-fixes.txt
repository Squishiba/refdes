1 (HIGH) page_count_error in a committed lockfile was nondeterministic, 1.3 KB
--------------------------------------------------------------------------------
`_unreadable_reason` folded *every* distinct line pypdf logged into one string.
pypdf narrates its own recovery while parsing a damaged file, and some of those
lines quote the live address of an object it found:

    Root found at IndirectObject(2, 0, 139905524280560)

That address is ASLR-dependent, so the same bytes recorded a different reason in
`.refdes/citations.yaml` on every `refdes fetch` -- and the lockfile is committed.
The review measured 1307 chars over 18 YAML lines where base had 90 chars, and a
different address in each of five separate processes. 5 of 40 randomly shredded
PDFs hit the address case.

Three changes, because there were three separate ways for the record to be wrong:

  a. Only the *first* logged line is folded in. F2 asked for pypdf's logged
     words because the exception it finally raises only says the stream ended
     while the log says why ("EOF marker not found") -- one line is that fact.
     The rest is recovery narration, and that is where the address repr lives.
     Measured: across 400 randomly damaged PDFs the first logged line was always
     the complaint and was never the address repr (.scratch/probe_first_logged.py).

  b. An address is stripped anyway, belt and braces: `_PYPDF_ADDRESS_REPR` keeps
     the object and generation (`(2, 0)`) and drops the address, and
     `_PYPDF_HEX_ADDRESS` covers a bare `0x...`. So a later pypdf version that
     puts the address first still cannot reach the file.

  c. The reason is bounded at `UNREADABLE_REASON_MAX = 200`. Keeping one line is
     not by itself a bound -- pypdf logs single lines that embed a whole dict
     repr ("Expecting a NameObject for key but found {'/F1': IndirectObject(...)}")
     -- so the clamp stays.

Measured after: 400 damaged PDFs, max reason length 200, zero over cap, zero
address-style survivors. Measured across processes: identical.

2 (MEDIUM) _owning_pypdf_logs permanently leaked propagate = False
--------------------------------------------------------------------------------
Round 1 removed the level mutation and left the `propagate` save/set/restore,
which is the same class of bug. Two blocks interleaving on two threads meant the
flag was never put back -- 300/300 in the review's reproduction -- so the host
application's logging stayed blind to pypdf for the rest of the process. The
function's own docstring reasons about "a threaded server", and `refdes serve`
is threaded.

  - `_PYPDF_ROUTE_LOCK` + `_pypdf_route_depth`: only the outermost of any number
    of overlapping or nested blocks saves the flag and only the outermost puts it
    back. The lock guards the count and the saved value, not the read.
  - What is restored is the *caller's* setting, read at entry, not refdes's
    opinion of it. A host that muted pypdf before calling in is not un-muted
    afterwards.
  - `_PypdfLogCapture` now takes a thread name and drops records from any other
    thread. There is one `pypdf` logger and a record cannot say which read
    produced it, so two concurrent reads used to fold each document's complaint
    into both reasons -- a message naming one document's damage, quoted in
    another's error.

`propagate = False` itself is kept: F2's test
(`test_refdes_reads_the_pdf_so_refdes_owns_the_report`) requires that pypdf's
words do not reach the host's logging either, and removing it fails that test.
