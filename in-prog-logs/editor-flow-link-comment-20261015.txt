Mechanism (verified by reading src/refdes/patcher.py): `_plan_key_line_removal`
deletes the whole `verb:` entry (replacement="") when the last link target
leaves (call sites via len(elements)==1 and via the scalar path). Its comment
guard scans only the line tail after the value's end mark and the key-colon ->
value-start gap. A comment inside a multi-line flow node (`satisfies: [\n
REQ-001  # keep me\n]`) sits between the value's own start and end marks --
invisible to both checks -- so the plan applies and the comment is destroyed.
The trailing-comment control (`satisfies: [REQ-001]  # keep me`) hits the tail
check and refuses 422, which is why the gap went unnoticed.

Reproduction (per AGENTS.md, real EditorApp HTTP): scratch project under
.scratch/editor-flow-link-comment-20261015/proj005 (refdes init, hardware@3,
REQ-001 + three log items), server started with
PYTHONPATH=<worktree>/src env-pinned (verified via /proc/<pid>/environ) and
`python -m refdes.cli` (the venv console script imports a different editable
checkout -- same trap the sweep hit). POST /api/item/LOG-001/edit
(remove_link satisfies REQ-001) -> 200 applied, after-file shows the whole
satisfies entry and `# keep me` gone. LOG-002 (trailing comment) -> 422
refused. LOG-003 (no comment) -> 200 clean. Matches the finding exactly.

Fix (narrow refusal, consistent with the patcher's standing rule "does not
destroy comments it cannot re-home"): `_plan_key_line_removal` now also scans
the value node's own span for a `#` that sits outside every scalar span
beneath it (`_comment_in_value_interior` + `_scalar_spans` in patcher.py).
A `#` inside a quoted scalar is data, not a comment, so the quoted-target
control still applies. Reuses the existing refusal message.
