## Verified by running, not by reading: when the lock file appears
Scratch project `.scratch/lockprobe` (`refdes init` + `refdes new requirement`
+ `refdes id`), served with
`python -m refdes.cli serve --no-open --port 8791 --token-file .../launch.txt`,
stopped with `kill $!`.

1. After `refdes init` + `refdes check`: `.refdes/` holds `schema.json` only.
2. `serve` started: `.refdes/` still `schema.json` only. **No lock at startup.**
3. `GET /api/revision` and `GET /api/item/REQ-001`: still no lock.
4. One `POST /api/item/REQ-001/edit` (`set_field status=active`, HTTP 200
   `applied`): `.refdes/serve-write.lock` appears, 0 bytes.
5. A stale-revision `Conflict` and a gate-blocked `Invalid` (bad enum) both
   returned before the file was touched -- neither created it. The lock is
   taken at edit.py:458, after the gate, so only a save that is actually
   about to be written reaches it.
6. Deleting the file and doing a *create* (`POST /api/items/create`, HTTP 200
   `created`): it did **not** come back. `create_item` takes only the
   in-process `write_lock_for` (edit.py:946-954); `_disk_write_lock` is called
   from `_apply_locked` alone. So the lock file belongs to the *edit save*
   path. Deleting it and then saving again did bring it back.
   (Worth flagging as an F2-adjacent follow-up -- a create is still not
   serialized across processes. Not this task's fix.)

So the doc claim to write is "the first save", scoped to an edit -- not "the
first launch" and not "any write".

### One test was passing vacuously, and that was a real finding
`test_init_gitignore_holds_when_the_project_is_one_directory_of_a_repo` passed
*before* the fix, with the lock path in its list. `git check-ignore -v a b c`
exits 0 if **any** of the paths is ignored -- so the two already-covered paths
were vouching for the third. It now probes one path per call, and it fails
without the fix like the rest. The batch form is noted in the test's docstring
so nobody re-introduces it. (Worth remembering for any other multi-path
`check-ignore` in the suite; I only fixed the one I was touching.)

The five new `covering`/`pattern` parametrize cases pass before the fix too,
necessarily: the coverage check has nothing to say about a file that is not
being written yet. They are regression guards for the entry, not baseline
failures.
