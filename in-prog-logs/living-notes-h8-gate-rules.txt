Decisions written BEFORE coding, per AGENTS.md / task instructions.

1. Where the rules live
   RELEASE_GATE_DEFAULTS (model.py) gains `open_tasks` and `captured_edits`,
   each {release: false, revision: false}, appended after
   unaccepted_workspace_moves. That automatically makes them RULE_NAMES
   members (RULE_NAMES = tuple(RELEASE_GATE_DEFAULTS)) and overlay-validated
   (schema.py iterates RELEASE_GATE_DEFAULTS). Two _rule_* functions in
   _RULES. evaluate_gate() and stamp() need NO change — verified by reading
   them: evaluate_gate iterates RULE_NAMES and consults
   project.release_gate[name][kind]; stamp only refuses when
   r.enabled and r.offenders. Confirmed no change needed.

2. open_tasks reads the existing fold, not a re-implementation
   chains.fold_tasks is the fold threads_projection uses (one per tip,
   memoized per component on the ChainGraph). The rule builds one
   chains.build_graph(project) and calls fold_tasks per local item as a
   start, deduplicating tips by identity (threads.py's own `seen`-by-id()
   pattern). Do NOT import threads.py from lifecycle.py: threads.py imports
   lifecycle at module level (_derived_problems reads the gate's own
   predicates), so a top-level lifecycle->threads import is a cycle, and an
   in-function import would be the projection's whole derived-row/capture
   machinery paid per stamp for nothing the gate needs.

3. Solo entries ("thread of one") count
   fold_tasks's own docstring: an entry with no follows: at all is "a thread
   of one — the ordinary log head 'the first task list' is written on" and
   yields one fold. threads_projection deliberately omits edgeless lone
   entries from the *index* (byte-identity for non-threaded projects), but
   that is an index posture, not a policy about tasks. A gate that missed an
   open task on a first log entry (before anyone has written a continuation)
   would be a hole in exactly the case H6 put tasks: there for. Provisional
   decision: count every tip of every component rooted at a local item.
   => Open question for the owner.

4. Imported tips/items do NOT count
   Every other rule selects over project.local_items (baselines, coverage,
   validation all exclude imports). Offenders name the tip and task id —
   an imported entry's open tasks are the other project's business. Tips
   whose item is not local are skipped; same for captured_edits findings on
   imported items.

5. Conflicting (ambiguous) task fold at a tip: BLOCKS
   Per the task's recommendation: the gate must not pass something it
   couldn't read. Offender: "<tip>: conflicting task list (task
   reconciliation required)" — "task reconciliation required" is
   fold_tasks's own phrase.

6. Offender wording (open_tasks)
   Existing rules return bare ids; the table joins offenders with ", ", so
   no offender may contain a comma. Style: "<tip>: open task <task-id>";
   a row whose id is absent (validation permits id-less rows) names it
   "#<position>" in the folded list. Sorted like every other rule.
   Multiple open rows at one tip -> one offender each.
   => Open question for the owner (wording).

7. captured_edits uses the H3 diagnostic as-is
   history.edited_after_captured(project) is the existing source ("do not
   recompute"); the rule maps each finding to `item.id or item.key` — the
   same label build.warn_edited_after_captured prints. Malformed task rows
   are a build *error* (_field_error), so the error floor stops a stamp
   before the gate; a row with no state is legal and not open, so it does
   not block. If the history store cannot be read (HistoryError/OSError),
   the rule returns no offenders — matching H3's "the check declines, the
   build proceeds" posture; the build's own warning already names the
   unreadable store. HistoryKeyError (corrupt key) is likewise left to the
   build, where it becomes an error before any gate runs.

8. revision half
   Both rules default {revision: false} like nearly everything ("nothing
   defaults on for revision"). The overlay can still turn the revision half
   on — schema validation accepts it and evaluate_gate consults it; that is
   the existing posture of all eight rules and I implement no special
   refusal. Whether these two *should* be allowed for revision at all is
   => Open question for the owner (recommend: allow, same as the others).

9. Default-off proof shape
   A stamped release's `gate:` block records EVERY rule including skipped
   ones (that is main's posture: baseline.gate["unverified_requirements"]
   == "skipped" in test_lifecycle.py), so stamped baselines unavoidably
   gain two "skipped" lines — byte-identity with main is impossible for the
   file; the test therefore pins the exact stamped baseline bytes (modulo
   stamps of wall-clock fields) and pins the CLI stdout, asserting the new
   rules read "skipped" and every existing rule's status is unchanged.
   Exit code alone would prove less; stdout + baseline file is "the stamped
   output".

10. Tests: appended to tests/test_lifecycle.py (332 lines — not huge; the

    hardware@3 (like tests/test_threads_projection.py) so `log` carries
    tasks:/follows:/status for free.
    Also tests/test_project_settings.py's exact-defaults equality dict gains
    the two entries (it pins the exact dict).

Owner: items 1/3/4 keep as implemented; item 2 keeps the wording AND the
offender should link to the actual task row. Decisions before coding:

(a) Everywhere gate offenders are shown -- found by grepping evaluate_gate /
    gate_results / offenders across cli.py, render.py, templates/, serve/:
    exactly ONE rendering: cli._print_gate_table (cli.py, the "blocked --
    not stamped:" table on stderr, reached from _run_stamp only). The
    baseline's gate: block maps rule->status (no offenders); items.json /
    index payloads carry no gate data; no template touches gates or
    offenders; serve/edit.py's "delta diagnostic gate" compares BUILD ERROR
    sets, never release-gate results. So (c) applies as its escape hatch:
    offenders never render as HTML today -> no anchor work, no new page;
    reported here and in the PR.

(b) Row lines: the loader ALREADY has a position tracker -- parse._LineLoader
    tags EVERY nested mapping with __line__ (start_mark.line+1), including
    tasks: row mappings -- both item load paths (markdown front matter at
    parse.py's _load_line_marked(text, _LineLoader), and parse_list_file)
    use it. _build_item stores fields via _strip_lines(value), which is
    exactly what discards the row lines (it must: __line__ inside fields
    would poison content_hash/semantic_digest), so Item.fields carries no
    row position today. Reuse, not a new tracker: _build_item captures the
    row __line__ values for `tasks`-type fields BEFORE stripping and keeps
    them on Item.field_lines (new dataclass field, default empty; consumed
    only by the new gate rule). The fold hands back the declaring entry's
    own fields["tasks"] list VERBATIM (chains._fold_from_tip via declared_of),
    so tip_tasks.rows' index i == field_lines["tasks"][i] == row i's line.
    Fallbacks, each said here rather than faked:
      - tasks: inherited from a `defaults:` block -- parse strips the
        defaults mapping before merging, rows arrive line-less -> the
        offender names the DECLARING entry's own line (file:source_line).
      - a malformed (non-mapping) row has no line -> same entry-line fallback
        (its build error already stops the stamp before the gate anyway).
    The line named is the task row's own line (flow rows: their single line;
    block rows: the row mapping's start, i.e. its `- id:` line).

(d) The conflicting-fold offender cannot point at a `tasks:` line: the
    ambiguity IS the tip declaring no list itself (the refusal happens
    between equal-distance ancestor declarations), so it names the tip's
    own entry line (file:source_line) -- the entry the author must open to
    resolve the conflict.
