PART 1 — projection fixes (threads.py, plus one helper in chains.py)

a. Ambiguous status fold vs "no status".
   Problem: chains.fold_at_tip returns (None, None) for BOTH "two entries tie
   at equal distance declaring different statuses" and "nothing ever declared
   status" — the (value, source) pair literally cannot tell them apart, so
   threads._verdict collapses both to verdict: null. The task fold already
   keeps these apart the only way it can: fold_tasks records what its
   declared_of was asked about (TipTasks.ambiguous). The field fold has no
   equivalent, and threads.py must not grow a second fold. Decision: add
   chains.TipFold + chains.fold_field_at_tip — the same _fold_from_tip walk
   with fold_tasks' recording trick — and make fold_at_tip a thin wrapper over
   it (its equivalence-with-resolve_current_with_source test stays the proof).
   threads._verdict then reports an explicit verdict state: a declared dict
   gains "state": "declared"; an ambiguous fold yields
   {"state": "ambiguous", status/declared_by/declared_on null, concluding:
   false}; an undeclared thread stays verdict: null. State name "ambiguous" is
   the word §5 rule 3 and the tasks block already use.

b. All-malformed declared task list.
   Problem: _tasks derived state from the post-filter rows list, so a declared
   non-empty list whose rows are all malformed reported "cleared" — a lie
   (the fold never saw an explicit tasks: []). Decision: state comes from the
   RAW declaration (empty list -> cleared, non-empty -> declared); rows is
   still the filtered list (validation owns the error); when any row was
   dropped, the block gains "malformed": true (conditional key, same posture
   as open_since).

c. Thread-list ordering.
   §5 and §6 order entries WITHIN a thread (thread_entries' oldest-first) and
   say nothing about ordering the LIST of threads. The code sorts views by
   root ref. Decision: keep the code, fix the docstring ("ordered by ref");
   add a test pinning ref-order with ids whose dates sort the other way
   (sabotage: sorting by root date fails it).

d. "rows verbatim" wording.
   Wrong in threads.py's module docstring and docs/output.md: open rows gain
   open_since and malformed rows are dropped. Fixed both to say: rows are
   copied; open rows gain open_since; malformed rows are dropped.

e. _scope and resolved_links.
   Code already reads item.resolved_links (correct per AGENTS.md) but no test
   pinned it: with every fixture link bare, raw links and resolved_links are
   equal. Added a fixture hand-authoring a composite `addresses:
   [REQ-001@<key>]` target (the test_keys_links.py pattern: mint keys, rewrite
   the YAML, reload) and asserting the thread's derived row still names
   REQ-001. Sabotage: reading item.links instead fails the test.

f. docs/output.md fork example showed forked:true with two tips but one
   branch. Made honest: both branches shown.

PART 2 — `refdes thread <ref>` + capture line

Capture line: threads_projection is the one query service (§6), and the CLI
must not recompute, so the capture fact joins the PROJECTION: each thread view
gains "captured": [{entry, kind, occurred_at}] for its members, read through
history.capture_index (read-only, no clock — occurred_at is store content, so
projection bytes stay clock-independent; a followed event deliberately carries
no occurred_at per H2, so the time is rendered only when present — the §6
sketch's timestamp only exists for explicit `history capture` events).

CLI shape: new cmd_thread in cli.py next to cmd_index/cmd_ls; resolves <ref>
by display id then surrogate key to its thread's projection entry and renders
§6's sketch: header (one tip / forked with both tips), capture line(s), tip
line(s), tasks with age, derived block.
- Two separately labelled groups with separate numbering (binding rule):
  authored tasks are numbered 1./2./... under "Tasks at tip:" (forked: "Tasks
  at <tip>:"); derived rows are never numbered at all under "Derived
  (self-closing):" — unnumbered is the strongest possible reading of "never
  shares numbering" — and derived rows carry no tickable state.
- Open task rows print the declaring entry and date: "(open since LOG-001,
  2026-08-30)". Relative "N days" appended ONLY under explicit --as-of DATE.
- Concluding verdict prints together with its tip's open tasks: the Verdict
  line sits directly above the task block and, when concluding while open
  tasks remain at that tip, says so ("concluding, N open task(s) at this
  tip"). Verdicts are never printed alone.
- Fork: every tip gets its own Tip/Tasks block; no thread-level status line
  exists (the projection has none).
- Task-block postures: declared rows / cleared ("none (cleared by X)") /
  undeclared ("none (never declared)") / ambiguous ("task reconciliation
  required", §5 rule 3's own phrase).
- Derived empty -> block prints "(none)" rather than vanishing (the group's
  presence is part of the two-groups structure).
- Unknown <ref> (not an item at all) -> clear error, exit 2 (mirrors
  `history capture`'s item-not-in-project row). <ref> is an item but on no
  thread -> clear error, exit 2. Load errors: reported to stderr, exit 1 with
  output intact (cmd_ls's posture). --as-of bad date -> exit 2.
- --json prints exactly the thread's projection entry (json.dump, indent=2,
  ensure_ascii=False, default=str — cmd_index's posture). --as-of + --json is
  refused (exit 2): --json is the projection, which is clock/relative-free by
  design.
- --as-of only ever renders relative spans; it never rewrites the projection.
- Writes: the command writes nothing itself; build runs seal_write=False like
  index/ls, so no seal/log-seal files appear. Tests: (1) --no-write run on a
  dirty tree leaves the tree hash unchanged; (2) a plain writable run creates
  no seal files on a project with an append-only log type; (3) output is
  byte-identical with time.time patched to different values (and no relative
  span without --as-of).
- State-name note: glyphs are [ ] open, [x] done, [-] dropped; wording lines
  (Verdict:, Captured:, Derived (self-closing):) follow §6's sketch where it
  gives words, otherwise are plain-CLI wording (the binding rules fix the
  STRUCTURE; no doc fixes this line text — every CLI line is like this).
