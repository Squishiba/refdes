## 1. Reading #132 first (what conventions it actually set)

Verified against `git show --stat 7c20d55` and the files it touched.

- `model.READ_ONLY_REFUSAL = "could not write this file (read-only tree?)"`
  plus `model.read_only_refusal(consequence="")`, which appends
  `" -- <consequence>; run with --no-write to silence this"` (src/refdes/model.py:696-708).
  The docstring says it exists so "a CI log filter is written against the
  string, and two spellings of one condition is how a user grepping for one
  misses the other (user-sim run 3, finding N2)".
- Two shapes, per `docs/cli-reference.md:41-97`:
  - *destination-naming* refusals put the path first:
    `error: cannot write <path> (read-only tree?) -- <what was lost>`, exit 2
    (revision/release) or exit 1 (history, revise).
  - the load-time shape is the per-file warning / parenthesised summary.
- `revise.Refused` (src/refdes/revise.py:689) is the explicit-write refusal:
  `_carry_forward_seals` / `_rewrite_baseline_file` raise it, `apply()` and
  `calc_rewrite.apply()` catch it, `_rollback()` the whole transaction, and
  return `ok=False` naming the file + "rolled back." — `revise` exit 1.
- #132's own words: "Explicit writes (`revise apply`, `calc-rewrite`, `keys
  adopt`, `keys restore`) still raise, which is what
  `test_an_explicit_write_still_raises_on_a_read_only_tree` pins and is the
  right answer: the tolerance belongs to writes nobody asked for." — so
  #132 documented the raise and F1 is that the doc/claim over-claims. The fix
  must narrow the *claim*, not invert the principle.

### 4.1 The defect the crashed session's own fix exposed

With `revise.py`'s diff applied, `revise` still tracebacked on the `tree`
layout, and the traceback was the interesting kind — the refusal came back out
of its *own rollback*:

```
refdes.revise.Refused: cannot write items/alpha/requirements.yaml (read-only tree?) -- ...
During handling of the above exception, another exception occurred:
  File "src/refdes/revise.py", line 1474, in _rollback
    textio.write_text(config_path, config_before)
PermissionError: [Errno 13] Permission denied: '.../refdes-project.yaml'
```

Three unconditional writes in the rollback path, each re-attempting a write the
filesystem had just refused, each on a tree that is read-only by definition:

- `restore_rewrites` wrote every rewrite back, including files this run never
  changed. Fixed by comparing before writing — the same property
  `_restore_seal_files` already documented and already relied on. The crashed
  session had added this one.
- `_rollback`'s `textio.write_text(config_path, config_before)` did not.
  `standard upgrade` *does* bump the pin, so the rollback has to put it back —
  but plain `revise` never wrote the config at all, and on a read-only tree
  that unconditional write is a `PermissionError` for nothing. Same
  compare-before-write fix. **This is the one the crashed session was missing,
  and it is what made `tree` still traceback.**
- `_restore_seal_files` already compares. Left alone.

### 4.2 The shape each of the six takes, and why

Same class, six different answers — because what each command *is* differs, and
a single rule would be wrong for at least four of them. Recorded here because
the reasoning is not visible in the diff:

| command | refusal | exit | why that and not another |
|---|---|---|---|
| `revise`, `calc-rewrite`, `standard upgrade` | `refused:` naming the file, whole transaction rolled back | 1 | The rename lands in some files and not others otherwise, which is not a rename. Rollback has to be defined *before* the first write for exactly this reason. |
| `stub-tests` | `refused:` naming **each** file refused; what landed stays and is reported | 1 | Its files are independent (one per workspace/board, holding only their own scope's stubs) and a written stub is the author's from the moment it exists — `generate()`'s own docstring says a later run "must never touch them". Rolling back would delete the author's work to satisfy a symmetry nothing needs. Recovery is sound: dedup is by declared link, so a re-run after `chmod` picks up exactly the missed stubs. Pinned by a test. |
| `id` | `project.error()` per refused file; nothing allocated for it | 1 | `allocate()` already had this rule for an id it could not *place* (`insert_into_list` returning None). The filesystem's refusal is the same fact about the same write, so it gets the same treatment rather than a second one. Two sites: the write-back and the ledger, and the ledger needs **different words** because by the time it is written the ids are already on disk and there is nothing to roll back. |
| `standard add-preset`, `remove-preset` | `error: cannot write refdes-project.yaml (read-only tree?) -- …` | **2** | Not 1: exit 2 is the code these two *already* use for "your config is not what you asked for it to be" (unknown preset → 2, not selected → 2, pinned by `tests/test_exit_codes.py`). A read-only config is one more way to arrive at that same place, and changing the code would break callers branching on it. |

## 6. Tests

`tests/test_readonly_explicit_writes.py`, 14 tests, one group per command.
Chmod-based, so each carries `needs_posix_bits`, which skips on Windows and
as root — the same skip and the same reason as
`tests/test_citation_path_hygiene.py:135-139` (root ignores the bit, and
`chmod a-w` does not stop Windows from writing, so the condition cannot be
produced at all there).

Beyond "does not traceback", the tests pin the things that were easy to get
subtly wrong:

- `restore_rewrites` / `_rollback` compare before writing — asserted by the
  whole-tree `revise` and `standard upgrade` tests, which are the only shapes
  that reach the rollback's own writes. A regression here is invisible to the
  `items/`-only shape.
- `stub-tests` keeps what landed, names what did not, prints both, and a
  **re-run after the tree is writable emits no duplicate** — the last one is
  the property the whole partial-write design rests on, and it is a separate
  test because nothing else fails if it breaks.
- `id` names both halves separately, and `allocated 0 id(s)` with an empty
  `allocated:` list in the ledger (a number that was never allocated must not
  be burned).
- `standard remove-preset` has **two** read-only shapes — the config file
  (the simulation copy is refused, nothing changed) and a writable directory
  (the copy is written and deleted, the real write is refused). Same message,
  different code paths, both tested; the second also asserts no `.scratch`
  litter.
- `test_keys_adopt_still_reports_the_operating_system_s_own_reason` pins the
  *documented exception*: `keys adopt` still reports the `OSError`'s errno and
  does **not** carry `(read-only tree?)`. Injected rather than chmod'd, so it
  runs everywhere. It exists so that a future change which adds the marker to
  those two commands fails a test, and the docs get corrected rather than left
  claiming a filter catches them.

## 7. Docs narrowed, not inverted

F1's third point was that the docs contradict each other, and the crashed
session's log had already worked out the right response: **narrow the claim,
don't invert the principle.** The tolerance still belongs to writes nobody
asked for; what was false was the blanket "no command prints a traceback"
without the command list.

- `docs/cli-reference.md` — the destination table gains four rows (the revise
  engine's item files, `id`'s write-back and ledger, `stub-tests`, and the two
  preset commands); `keys adopt`/`keys restore` become an explicit row saying
  their message does *not* carry the marker; and "Match on `(read-only tree?)`
  — it is the one string every read-only refusal carries" becomes "almost every
  … (the two exceptions are called out below)", since `build`'s site-directory
  refusal was already the third exception and the text was over-claiming by one
  and by `keys`.
- `docs/design/keys.md` §2 — the "any other explicit write (`keys adopt`,
  `keys restore`) | raises, as before" row is the one F1 called out as reading
  as the complete list of raising commands. Replaced with rows for all six, and
  the `keys` row now says what it actually does (refuses, exit 1, OS's own
  reason) instead of "raises".
- `revise.write_rewrites_verified`'s docstring claimed "Explicit write commands
  (`revise apply`, `calc-rewrite`, `keys adopt`, `keys restore`) call
  `write_rewrites` directly and keep raising" — false for the first two since
  this change. Rewritten to name the two hooks and why they differ.
- `revise.write_rewrites`'s own docstring said `on_error` left None means "every
  explicit write command". Also false now; it names which two still leave it
  None.

Changelog fragment: `changelog.d/readonly-explicit-write-refusals.fixed.md`,
per `changelog.d/README.md` (kebab slug + category, `- ` bullets, no headings).
The existing `readonly-seal-baseline-writes.fixed.md` (from #132) says "no
command prints a traceback because a destination isn't writable", which F1
quotes as one of the two false claims — left alone, because it was true of what
#132 changed and this fragment is the one that makes it true of everything. Noted
here rather than silently rewritten, since rewriting another PR's fragment to
match a later change is not obviously the right call.
