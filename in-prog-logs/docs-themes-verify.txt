## Possible bugs (code, NOT documented; listed in PR body)

(a) theme.py render_theme_css root_names (lines 640-644) excludes from
`:root` every colour token that is overridden in dark with a value differing
from light — which is every colour token of every built-in theme. Result: the
LIGHT side of a built-in theme's palette (and of any project `light:` /
flat-pair override of such a token) is never written to theme.css.
Evidence: p-flat (theme: paper) theme.css starts ":root {\n}" (empty) and
`grep -c faf6ee` = 0 — light mode renders the shipped stylesheet's palette,
not paper's cream; p-lightonly (theme: paper + light: --bg '#fffdf7') has
grep -c fffdf7 = 0 in theme.css. The light block emitted for a light-only
override is [data-theme="light"] only (theme.py:657-661), so data-theme
pinning of light also fails for built-ins. The design intent in theme.py's
own docstring (lines 586-601) matches the DOC, not the code, which is why the
doc stays and the code is filed as a bug. test_theme.py never exercises
"token overridden in BOTH palettes" emission, so the suite passes.
(b) consequence of (a): the page's gallery tables ("what a reader would
actually see", gen_themes.py docstring) are light-mode-inaccurate for
high-contrast/paper/slate. Tables are generator output gated by
test_themes_page.py — not doc-fixed.
