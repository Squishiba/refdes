## F2 — init's "gitignored" paren was hardcoded (cli.py, scaffold.py)

`cmd_init` printed `wrote .vscode/settings.json (gitignored -- ...)` on
"init wrote the file" alone, never on git's answer. The key subtlety:
#328's helper `_gitignore_addresses` answers "has the project stated a
position" — a winning `!` negation is exit 0 there, so reusing it for the
announcement would have printed "gitignored" in exactly the report's
negation shape. The announcement needs the *ignored* answer, which is
git's `check-ignore -v` exit code plus the winning pattern read from the
source line (`!`-prefixed = tracked). Added `scaffold.vscode_settings_ignored`:
`_git_ignores` mirrors `_git_covers`' path probe with a new
`_check_ignore_ignored` verdict (parses `source:line:pattern<TAB>path`,
quotes stripped for git-quoted patterns); outside a repo the literal
`_literal_ignores` answers (a negated line is not ignored). NOT-branch
message names what a commit ships. The gitignored wording is byte-equal
to the old one, so `test_cli_announces_the_vscode_settings_file_it_wrote`
(non-repo tmp_path — init appends there, gitignored is true) pins it
unchanged. Parametrized CLI test covers `.vscode/*`+`!.vscode/*`, bare
`!.vscode/settings.json`, `.vscode/`+`!.vscode/` (all NOT) and `.vscode/`,
`/.vscode` (gitignored), each asserted against a hand-run
`git check-ignore` exit code.

## F3 — new `.gitignore` skipped the coverage question (scaffold.py)

`_ensure_gitignore_entries` wrote all entries when the file did not exist
(`if not os.path.isfile(path): write_text(all)`). Reproduced the report's
case: project nested in a repo whose root ignores `.refdes/` →
`check-ignore` says the `.refdes/*` entries are covered, init wrote them.
Chose to fix the write (not just the message): git can answer for a
path not on disk (`--no-index`), and the patterns that cover a fresh
project's files live above it — repo-root `.gitignore`s and
`core.excludesFile` (verified: check-ignore reports the global file as
source, and reads repo-local `core.excludesFile` config). New-file path
now runs the same `entries -> missing` comprehension as the append path,
with `""` as the text the project has: outside a repo the literal set
over no file writes everything, as before; a fully-covered project gets
no file at all (an empty `.gitignore` announces nothing) and the CLI
prints no `wrote .gitignore` line — the announcement diff
(`added_gitignore_patterns`) covers this with no change. No docs change:
cli-reference.md already promises "skipped for a path an existing pattern
already covers"; F3 makes the create path keep that promise. Tests: root
`.gitignore` covers `.refdes/*` only (vscode + lock still written, ground
truth probed by hand), full coverage → no file, `core.excludesFile` → no
file, and the CLI announcement line lists exactly the written entries.

## Follow-up: machine-local git rules are not coverage (#328 review, finding 2)

Design flaw in the F3/#328 helper: `git check-ignore` consults the
machine's global `core.excludesFile` and the clone's `.git/info/exclude`
too, and init counted their wins as coverage -- so an author whose global
config ignores `.refdes/` got NO project `.gitignore`, and teammates'
clones came up untracking (then `git add -A`-committing) refdes outputs.
Only rules in the project's own `.gitignore` files are shared; they are
the project having stated a position.

- scaffold: new `_source_is_shared_gitignore` (check-ignore's source is
  shared iff relative to the toplevel, basename `.gitignore`, not under
  `.git/`; git prints repo sources relative, the excludesFile absolute)
  and `_check_ignore_source` (winning pattern + source). The append-path
  `_check_ignore_verdict` now returns True only on a SHARED win; a
  local win is False (project text silent -- repo rules outrank local
  ones, git precedence). F2's trio
  (`vscode_settings_ignored`/`_git_ignores`/`_check_ignore_ignored`)
  became `vscode_settings_state`/`_check_ignore_ignored_state` with four
  states: project-ignored / tracked / local-ignored / unaddressed.
- cli: reads the state BEFORE `scaffold.init` runs (init's own appended
  line masks the local-rule case); a new third paren
  "(gitignored by a machine-local rule only -- the .gitignore line init
  added makes it ignored for every clone; ...)".
- Tests: 5 new (append path and create path under a global-excludes and
  under an info/exclude rule; CLI local-rule paren), all red on the
  branch tip before the fix, green after. A 6th guards project-negation
  beats local-rule (green both sides). Tests set GIT_CONFIG_GLOBAL to an
  empty throwaway under tmp_path (GIT_CONFIG_COUNT for the key) so real
  global config is never consulted.
- Changelog: the three init fragments updated to the shared/local line.

Full-suite run caught what the targeted runs missed: a PRE-init state
probe cannot see directory rules -- git matches a `.vscode/`-style
pattern only when the directory exists on disk, and the directory is
init's own first write (init writes .vscode/ before appending
.gitignore, which is why the append decision sees dir rules). Rebuilt:
`vscode_settings_state(cwd, added, local_rule_pre)` probes the
POST-init world (file probe, dir probe for `!dir/`); init's appended
line is read from `added` (vscode in added = no project position,
gitignored; with a pre-init local-file-rule win = local-ignored); a
local winner in the probe branch means the project covered the entry
by dir-track, so clones follow the project = tracked. 105 scaffold
tests green after the rebuild.
