Step 3, final record — whole command line vs per sub-command:
- Docs: /docs/permissions describes the `bash` permission as "running shell
  commands (matches parsed commands like `git status --porcelain`)". The
  phrase "parsed commands" suggests matching happens on commands extracted by
  a shell parser (i.e. per sub-command for `&&`/`;`/pipelines) rather than on
  the raw line, but neither /docs/permissions nor /docs/config states it, and
  no worked `&&` example is given.
- NOT DETERMINED FROM THE INSTALLED BUILD: the install here is a 177 MB
  compiled binary (~/.local/agents/node_modules/opencode-ai/bin/opencode.exe)
  with no readable source next to it, and the orchestrator told me to stop
  digging through it rather than spend a permission prompt per grep. So this
  is the honest state: docs only, unverified against the code.
- Does the leading `*` cover both? Mostly, yes: with `*` on both sides a
  pattern is a substring test, so it matches a whole line containing the
  fragment AND a single parsed sub-command containing it (leading `*` matches
  the empty prefix, e.g. "rm -rf b" on its own). Two cases where a
  per-sub-command model could still differ from a whole-line model, because
  it depends on what text the parser hands the matcher: a redirection
  (`echo x >/tmp/y`) and an env-assignment prefix (`PYTHONPATH=/tmp/x python`)
  — if those are parsed off rather than kept in the matched text, the bash
  rule may not see them. That is exactly why the `/tmp`
  `external_directory: deny` rules are the backstop: they trigger on the path
  a tool touches, not on the shape of the command line.
- The orchestrator will run one live check after merge; that settles it.
