## B4 — double-counted deleted key

Reproduced on the scratch project (delete the minted `key:` line of REQ-001 after
stamping `r1`, then `refdes -c ... check`):

    ERROR   items/reqs.yaml:3 [REQ-001] — key deleted since baseline 'r1': was 'ym4xxds2j3q', ...
    WARNING items/reqs.yaml:3 [REQ-001] — key deleted since baseline 'r1': was 'ym4xxds2j3q', ...   (byte-identical)
    2 items, 1 errors, 1 warnings
    exit=1

Same pair under `--no-write check`, `--no-write build`, `build`.
Two call sites, same predicate (`deleted_key_records`), same message
(`deleted_key_message`):
  - `keys._validate_deleted_keys` -> `project.error` (runs inside `build()` via
    `keys.validate()`, build.py:3057)
  - `keys.report_deleted_keys` -> `project.warn` (runs in `mint_missing()`, i.e. every
    `loader.load_tree`)

Severity decision (from the report + docs, not feel):
  - docs/design/keys.md Layer-4 table: "no item declares K; an item with display id D
    has no key | **key deleted — error**"
  - docs/troubleshooting.md:210 lists the message with a remedy among the errors.
  - run-5 report §7/B4: the complaint is the double count ("counts ... two higher than
    the number of things that are wrong"), and the ERROR is the one that carries the
    remedy the user followed.
  => keep ONE ERROR, drop the load-time WARNING.

Checked that dropping the warning silences nothing anywhere: `audit` and `ls` print 0
occurrences of "key deleted" today (verified on the scratch project: `--no-write audit`
-> 0, `--no-write ls` -> 0, `--no-write index` -> nothing on stderr), because they print
only the load-time errors captured before `build()` runs. Only `check`/`build` print it,
via `cli._report`, and they print the ERROR too. `report_deleted_keys`'s only caller is
`mint_missing`, and the minting protection itself lives in `missing_assignments` (which
re-derives `deleted_key_records` in the same load), so the `.refdes/` record reads the
perf log (in-prog-logs/perf-editor-save-single-build.md) relies on still happen in
load_tree.

## B5 — retired id does not resolve in serve API / editor index

CLI behavior verified on `.scratch/b45` (REQ-001 records `former_ids: [REQ-900]`):
    refdes ls REQ-900  -> "REQ-001  requirement  The rail shall supply 3.3 V. (formerly REQ-900)" exit 0
    refdes ls req-900  -> same (free-text search is case-insensitive)
    refdes ls REQ-001  -> row without the marker
    refdes ls NOPE-999 -> "no items match" exit 0
    refdes index --compact -> rows carry "former_ids": ["REQ-900"] (and "key": null on a
      read-only load, which mints nothing)
So the CLI resolves a retired id to the live item. `refdes serve`'s `/api/item/<ref>`
(`serve/api.py:_find_item`) tries only `project.items` then `item_by_ref`, so a retired
id 404s; `editors/vscode/extension.js:itemsById()` indexes only `item.id`, so the hover
never even asks.

Fix: `_find_item` consults `project.former_ids` (populated by `ids.collect_former_ids`
via `build.validate_former_ids`, which `loader.load_readonly` runs, so the serve snapshot
has it) after the existing spellings; `itemsById()` indexes `item.former_ids` too, with
the live id winning any collision. Hover markdown already prints
`_formerly known as ..._` from `view.former_ids || item.former_ids` (extension.js:272),
and `provideHover` then fetches `/api/item/<hovered token>`, which now resolves.
