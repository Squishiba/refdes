## Decisions (written BEFORE coding, per the task)

1. WHERE: new module `src/refdes/threads.py`.
   Justification: the function composes chains + build + blocked + citations +
   lifecycle. It cannot live in chains.py (lifecycle imports build, build
   imports chains — a module-scope `from . import lifecycle` in chains.py would
   be an import cycle), nor in build.py (build is the producer, not a consumer
   of lifecycle), nor in render.py (render is already 1300 lines and H7b/H7c
   must import the view without pulling the site renderer). `threads.py`
   imports chains/blocked/lifecycle/model only; render imports it.
   Public surface: `threads_projection(project, *, graph=None) -> list[dict]`,
   JSON-serialisable, one entry per thread.

2. VERDICT FOLD PER TIP: H7a needs, per tip, the folded `status`. On a settled
   thread that is exactly `chains.resolve_current_with_source(tip, "status")`.
   On an unmerged fork that fold is undefined (None) by design, but §5's
   worklist table says "forked values remain branch-local", so each tip must
   still carry ITS OWN branch's folded verdict. There is no public per-tip
   field fold (fold_tasks is tasks-only), so I add ONE tiny public wrapper in
   chains.py: `fold_at_tip(project, tip, field, *, graph=None) -> (value,
   source)` = `_graph_view` + `_fold_from_tip` + `_declares` — literally the
   machinery resolve_current_with_source uses, anchored at a given tip instead
   of at "the component's one tip". No second fold is written; the docstring
   states the one-tip equivalence. threads.py uses it uniformly (one rule for
   settled and forked alike; for one-tip threads a test asserts equality with
   resolve_current_with_source).

3. WHAT COUNTS AS A THREAD: every connected component of the follows graph —
   same definition as chains.thread_entries (§8) — restricted to items with a
   follows edge in either direction (chains.is_threaded). A lone entry with no
   follows either way is NOT its own thread in this projection (that is
   render.thread_view's posture too, and it is what keeps a non-threaded
   project's payload byte-identical: no threads -> no `threads` key at all).
   Identity = `ref`: the thread's root (oldest entry by chains.thread_entries
   order), named `id or key or slug` like every other view. `entries` lists
   every member ref (so a client can map any item -> thread without walking),
   `tips` lists tips (len > 1 == fork), plus explicit `forked` bool.

4. SHAPE = THE BINDING RULES (§5, "output structure, not polish"):
   - Rule 1, two structurally separate groups: authored tasks live at
     tips[].tasks (per tip, fold_tasks verbatim rows); derived rows live in a
     thread-level `derived` list. Different keys, different item shapes; a
     derived row has no `id`/`state` fields, so it cannot sort into the
     authors' numbering, and nothing ever writes them back (the function
     mutates nothing; tree-hash test).
   - Rule 2, self-closing: derived rows are COMPUTED per call from the build
     state the lifecycle rules already consult (project.coverage, item.checks,
     project.blocked_chains via blocked.by_item, item.citations) — fix the
     gap, rebuild, the row is gone; there is no state to tick by construction
     (absent keys, not null state fields).
   - Rule 3, every open task shows its age, absolute only: each open row
     carries `open_since: {entry, date}` from fold_tasks' source entry and that
     entry's authored `date:`; the module imports no clock (guard test greets
     `datetime` out of the module source), so two runs on different wall
     clocks produce identical bytes; `--as-of` relative spans are H7b's.
   - Rule 4, a verdict never prints alone: each tip carries `verdict`
     (status/declared_by/declared_on/concluding) NEXT TO its `tasks` block in
     the same tip object; `concluding` mirrors blocked._is_settled's question
     (type declares satisfying_statuses:/verifying_statuses: and the folded
     status is in it; neither declared -> not concluding).
   - Rule 5 (gate) is explicitly NOT this phase's output (plan §H7), so it is
     absent from the shape entirely.
   - The fork rule: there is NO thread-level status/verdict key anywhere;
     a fork shows tips[].verdict with per-tip branch-local folds (decision 2),
     so the payload can never read as one current status.
   - fold_tasks' distinct no-list states are kept distinct as
     tasks.state: "declared" | "cleared" (rows: []) | "undeclared" (never
     declared) | "ambiguous" ("task reconciliation required", rows null).

5. WHICH DERIVED ROWS APPLY TO A THREAD: the thread's items = its members; a
   row also applies when its subject is what a member's OUTGOING resolved links
   point at (one hop, through item.resolved_links per AGENTS.md — never raw
   links): §6's decided example shows exactly that (a log thread carries
   `coverage REQ-... unverified` and `citation CMP-... unpinned`, neither of
   which is a thread member). Selection predicates are the lifecycle rules the
   plan names, verbatim (coverage stage open -> uncovered, stage != verified ->
   unverified (uncovered wins as the label), check ok False, blocked chains
   declared by a member, citation state unpinned/cache_missing). Rows are
   ordered coverage < check < blocked < citation, then by ref, deterministically.
   If this one-hop choice were wrong it would change user-visible output;
   §6's example is the docs' own answer, so this is following, not settling.

6. items_json(): `threads` inserted right after `coverage`, keyed presence =
   non-empty projection (absent-key convention, same as boards/captured).
   Golden fixtures: tests/fixtures/no_theme_build_hashes.json pins items.json's
   hash for a NON-threaded project -> key absent -> unchanged (must verify by
   running test_theme). The other two fixtures are resolved-schema dumps, not
   payloads. No test asserts the exact key set of the payload.

7. NOT BUILDING: no CLI, no serve/site panel/VS Code change, no stale-tip
   prompt, no writes (tree-hash test around the projection).

## Deviations from the design log (decided during implementation)
- Derived-row citation selection iterates item.citations states instead of
  calling the two lifecycle rules (see diff summary; the selection sets
  would need re-filtering anyway for the per-citation detail).
- Derived-row "problem" key (not "state") for coverage/citation rows, so a
  derived row can't be confused with a task row's `state`; check rows carry
  the factual `ok`/`margin` from CheckResult, blocked rows carry `stale`.
- items_json took the optional `graph` kwarg (not in the original design
  notes) because the existing perf test pins one build_graph call per
  render_site; the index CLI builds its own.
