## 2. Scope: every YAML file refdes loads, and what I did about each

`grep -rn "yaml.safe_load|yaml\.load|YAML(|ruamel" src/refdes/` plus
`grep -rn yaml_safe_load src/refdes/` gives the whole set. There are two
loader families and the config files are in the *other* one from item
files -- the same split `in-prog-logs/yaml-duplicate-keys.txt` §2 recorded
for PR #130.

**In scope, changed (hand-authored config):**

| file | read by | change |
|---|---|---|
| `refdes-project.yaml` | `schema.load_project` (schema.py) | refused |
| `refdes-schema.yaml` | `schema._load_schema_overlay` (schema.py) | refused |
| a `revise` mapping file | `revise.load_mapping` (revise.py) | refused |
| `refdes-project.yaml`, for a preset edit | `scaffold.add_preset` / `remove_preset` | refused |

The `scaffold` one is not in the brief's list and I added it deliberately:
it is the same file, and it is the only path that *writes* the config
without going through `load_project` (`add_preset` reads the file to span-edit
`standard.presets: [...]` and never loads the project). A config with two
`presets:` lines would have had the preset appended to the first while the
loader resolved the second -- so it was the one command where a silent
repeat would have *written* the ambiguity down. Test
`test_add_preset_refuses_a_config_it_could_not_read` pins it, including that
nothing was written.

`revise.load_mapping` is in because it is hand-authored YAML refdes loads and
already reports as a `SchemaError` (exit 2, `configuration error:`). A repeat
there is worse than a repeat in a config block: a rename mapping's whole job
is to say which old name becomes which new one, so two `REQ:` lines under
`prefixes:` drop one rename and apply the other.

**Out of scope, deliberately, with the reason:**

- **Everything under `.refdes/`** -- the id ledger, boards manifest, seals,
  baselines, history objects/events, `keys-adopted.yaml`, the citations
  lockfile. The brief says so, and it is also the right call: these are
  refdes's own output, so a repeat is a refdes bug rather than an authoring
  slip, and hardening them is a much wider question (seal hashes, baseline
  diffs and `audit` all read those files, and each would need its own
  decision about what a repeat means). Noted in the changelog fragment so the
  boundary is on the record.
- **The bundled standard** (`standards._read_yaml`, reading
  `standards/hardware/v3/base.yaml`, its `migration.yaml` and its presets).
  Shipped with the package, not hand-authored per project -- and
  `configcheck.py`'s own module docstring already states that principle
  ("Both check *project-authored* input only"), which I extended rather than
  contradicted.
- **`pages/*.md` front matter** (`pages._read_page`). Real hand-authored YAML
  refdes loads, and a repeat there *is* silent -- but it is page content, not
  a config file, and its whole diagnostic family is deliberately soft: an
  unparseable page front matter is a `project.warn` ("invalid page
  front-matter: ...", pages.py) that leaves the page rendering without its
  metadata, not a hard error that stops the load. Promoting it would be a
  separate decision about that family. `in-prog-logs/yaml-duplicate-keys.txt`
  §5 listed it as a follow-up; it is still one, and I am not quietly folding
  it in here.
- **`patcher.py`'s `yaml.safe_load` calls** (lines ~824, ~1456, ~1510,
  ~1773). One is a round-trip check of an emitted value, one is a
  before/after *projection* of item text for the revert comparison, and the
  docstring there says it uses the plain loader on purpose so `__line__`
  bookkeeping cannot make two identical items look different. Not config.
- **`revise.py`'s two `parse.yaml_safe_load` re-reads** (lines ~780, ~923) and
  `serve/edit.py`'s (`yaml_safe_load` on an existing item list file to decide
  whether an append can preserve every existing byte). All item files, all
  already #130's territory.

## 3. The fix: one detector, one message

### 3a. Detection -- `parse.py`, reusing #130's `_duplicate_keys`

`_duplicate_keys` was already the right detector and needed no change. What
was missing was a *loader* that runs it without #130's `__line__` tagging,
because `configcheck` walks every key of every block and would report the
bookkeeping key as an unknown setting in all of them.

- `_collect_duplicates(loader, node)` -- the collect-onto-the-instance half of
  #130's `_construct_mapping`, extracted so both loaders share it verbatim.
- `_DupSafeLoader` / `_PurePythonDupLoader` +
  `_construct_mapping_dupes` -- same `_duplicate_keys` walk, **no** `__line__`.
- `yaml_safe_load_checked(stream)` -> `(data, records)` -- the config-facing
  `yaml_safe_load`, with `yaml_safe_load`'s C-then-pure-Python retry so a
  syntax error keeps its byte-identical diagnostic.
- `_as_text(stream)` -- extracted from `yaml_safe_load`, shared by both.

So there is one detector, and the two loader families cannot disagree about
what a repeat is. `<<:` merge keys are still read before `flatten_mapping`
(inherited from `_duplicate_keys` itself), pinned by
`test_a_merge_key_is_not_a_repeat`.

### 3b. Reporting -- `configcheck.py`, following the existing path

`check_duplicate_keys(records, source)` raises
`SchemaError(f"{source}: {message}")` -- the same `SchemaError` every other
config problem raises, so it lands on the path that already exists:
`cli.main` (cli.py:2346) prints `configuration error: <msg>` and returns 2.
No new diagnostic family, no new exit code, no new handler.

Placement is deliberate and is the answer to the brief's "how a hard config
error stops the load":

- `schema.load_project`: immediately after the file is parsed, **before** the
  legacy-`refdes.yaml` check and before `_validate_settings`. Every check
  below it would otherwise be judging a mapping the file does not contain.
- `schema._load_schema_overlay`: immediately after the overlay is parsed,
  before its own `SCHEMA_KEYS` check.
- both are `check`ed before any item is parsed and before anything is
  written, since `loader.load_tree` calls `load_project` first.

Message shape, reused rather than rewritten: `_report_duplicate_keys`'s body
is now built by `parse._duplicate_key_message(record, remedy, context, extra)`,
with the two shared pieces pulled out as `_duplicate_outcome` (which value is
lost / that nothing is lost / the value is too long to quote) and
`_duplicate_where` (`(lines N and M)` / `, twice on line N`). The item-file
call site passes its `context` and its `; an 'id:' lost this way is a whole
item, not a field` clause; the config call site passes neither, so the two
messages cannot drift into telling different stories about the same document.

Config-specific bits that are genuinely different, and why:

- **Remedy.** The item-file one leads with a list entry that lost its `- `
  marker, which is a shape only items have. The config one is
  "Usually a hand-merge or a copied block left two spellings of one setting:
  keep the one you meant and delete the other." A test asserts the item-file
  remedy is *not* in the config message.
- **Every repeat in one error.** `configcheck.keys` already had the rule --
  "a block with two typos is one read of an error, not one per `refdes
  check`" -- so all repeats are named in the one `SchemaError`: the first
  written out in full (remedy + docs pointer), the rest after `Also: ...`
  in the compact form.
- **Docs pointer.** `docs_url.ITEMS_FIELDS_DOCS`, because the new
  troubleshooting entry sits in that same `## Items and fields` section (the
  retired-`refdes.yaml` config error is already there too). Anchor verified
  with `pages._slugify("Items and fields") == "items-and-fields"`, not
  guessed.

## 4. The wrinkle: line numbers on a config error

The brief was right that config errors carry none -- verified by running
it, on a `sit:` typo against a clean config (.scratch/cfgH):

    configuration error: refdes-project.yaml: unknown setting 'sit'. Did you
    mean 'site'?
    [exit=2]

No line anywhere, and `schema._validate_settings` is untouched by this diff
(`git diff src/refdes/schema.py` is only the two read sites and the import),
so this is main's behaviour too. But the brief is also right that this one
should carry lines, because the diagnosis of a repeat *is* two line numbers and
nothing else is useful about it. So `DuplicateKey.first_line` / `second_line`
reach the message through the shared builder, and the message reads:

    configuration error: refdes-project.yaml: duplicate key 'site' in one
    mapping (lines 1 and 6) -- YAML keeps the last, so the value on line 1 is
    lost. Usually a hand-merge or a copied block left two spellings of one
    setting: keep the one you meant and delete the other. See
    https://squishiba.github.io/refdes/troubleshooting.html#items-and-fields.

Lines are the real file lines: `load_project` parses the whole file, so no
slice offset is needed (unlike #130's Markdown front-matter path, which does
`_shift_duplicates`). Nothing else about the config family changed -- no other
config error grew a line, and the `file:` prefix every config message already
carries is unchanged.

## 7. Decisions I made that a reviewer might want to overrule

1. **`scaffold.add_preset`/`remove_preset` are in scope.** Beyond the brief's
   list. Reasoning in §2: it is the same file, and it is the one path that
   writes the config without loading it.
2. **`revise` mapping files are in scope.** They are hand-authored YAML refdes
   loads, already in the `SchemaError` family, and a repeat there drops a
   rename rather than a setting.
3. **`pages/*.md` front matter is out.** Reasoning in §2 -- it is page
   content, and its family is a warning by design. This is the one exclusion
   where a maintainer might reasonably disagree, so it is stated rather than
   buried.
4. **All repeats in one error, first one in full.** Followed
   `configcheck.keys`' existing rule rather than #130's one-error-per-repeat,
   because a `SchemaError` can only carry one message -- #130 can accumulate
   because `project.error` appends to a list.
5. **`breaking` changelog category.** `changelog.d/README.md` defines it as
   "existing projects must change". A config carrying a repeat that loaded
   yesterday now fails to load on every command, which is that by definition;
   the same reasoning as its sibling `duplicate-mapping-key.breaking.md` and
   `config-split-two-files.breaking.md`. Folding it into `fixed` would hide
   that, which is why the brief said to read the definition and decide.

3. **A duplicate in `.refdes/` state is still silent** (§2) -- and that is
   where the consequence is most expensive, since a repeat in a seal file or
   the citations lockfile changes what a build is compared against.
4. **`refdes-project.yaml` written by `refdes standard add-preset` /
   `remove-preset` is never checked after the write.** The span edit cannot
   introduce a repeat, so this is a non-issue in practice; noted only so
   nobody reads the refusal as a general post-write verification.
