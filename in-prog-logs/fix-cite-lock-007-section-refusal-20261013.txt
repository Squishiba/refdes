CITE-LOCK-007 -- int(resolved) on a lockfile `sections:` value crashes serve
=============================================================================

Finding (in-prog-logs/current-main-resweep-citation-restore.tsv, read from
the shared main checkout /home/jorb/work/refdes -- not present at the pinned
worktree base): src/refdes/serve/sources.py:371 `return int(resolved),
"section", detail`. A sound-shaped record whose `sections` value is not a
page number (`{Intro: nope}`) loads -- `citations._record_problem` types the
`sections:` mapping (:987-992) and `sections_sha256` (:993-1001) but never
the values -- and the serve routes catch only SourceRefusal.

Base: worktree fix/citation-section-refusal-20261013 at 8b6a52e (local main),

Decision: panel state, not a 422 (task/sweep wording deviation)
---------------------------------------------------------------
The sweep line phrased the wanted outcome as "SourceRefusal -> 422". The
module's own doctrine, verified in the tree at 8b6a52e, says this exact
shape is a panel state:

- sources.py `_cited_page` docstring: "a value that names no openable page
  is reported in the citation's own terms and the picker opens page 1 --
  never page 0, and never a guess at what 'xiv' meant."
- `page_payload` docstring: "A citation whose page this document does not
  have opens page 1 and says so in `cited.detail`, because refusing the
  whole document over a stale page number would hide the very thing the
  author needs to look at." 422 there is defined as failures of "the read
  itself" -- the PDF reads fine here; it is the pointer that is broken.
- docs/design/editor-pdf-picker.md:193: "Visible failure is a panel state,
  not an error page."
- The sibling test `test_a_section_whose_page_is_unusable_says_why_and_
  opens_page_one`: no resolved page, resolved-against-other-bytes (same
  elif chain, same remedy `refdes fetch --update`), `page: xiv`, page 99
  past the count -- all 200 + page 1 + detail naming the fix. A 422 here
  would make a garbage resolution stricter than a stale one with the same
  remedy.
- Mechanically, a SourceRefusal raised inside `_cited_page` would also
  crash `/sources` at this base (no catch until unmerged 403ab84 on the
  CITE-LOCK-005 branch) -- so "422" is not even the smaller change here.

Confirmed with the task owner before shipping (chose panel-state).

Fix
---
src/refdes/serve/sources.py `_cited_page`: replaced the second page grammar
`int(resolved)` with the shared `_page_number(str(resolved))` (the same
grammar `page:` above it and the loader use -- `citations.page_number`'s
docstring names exactly this two-grammars hazard, incl. page 0). A value
that is not one now falls through to the existing no-page return with a
detail naming the section, the path, the offending value, and
`refdes fetch --update --path <path>` to re-resolve. One fix site covers
both routes. Docstring extended to state the lockfile-value contract.

Valid-numeric controls: YAML int 3 -- the shape `fetch` writes -- already
opens page 3 via the existing `test_the_page_view_..._resolved_section_page`
test; the new test adds the string "3" control (accepted by `int()` before,
must stay accepted: `str()`-then-`page_number` keeps it) on both the page
route (open_at page 3 from section, no detail) and the file list
(open_page 3). Behavior tightening, both directions of the shared grammar:
`0`, `+3`, `3.5`, bools no longer open a page -- they name themselves in
detail. That is the documented "positive integer and nothing else".
