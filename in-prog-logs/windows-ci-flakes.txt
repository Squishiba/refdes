(b) tests/test_history_commands.py::test_redaction_events_are_not_redaction_targets
- Run 37099112528 attempt 1 (PR #162 branch write-locks-tier-a), windows-latest:
  `error: .refdes/history/events/f880bd78-....yaml: key '213312678452' is
  malformed: expected exactly 11 characters ... If YAML already converted an
  unquoted key and rewrote this file, its original spelling cannot be
  recovered here.` → `assert 1 == 0` at tests/test_history_commands.py:377.
- ROOT CAUSE (not platform-dependent at all): `history.redact()` stores
  `fingerprint = sha256(...)[:12]` — 12 hex chars — in the event's
  `successor_key` field. `load_events`/`append_event` validate that field with
  `keys.require_storage_key`, whose contract is "a surrogate key". When the
  fingerprint happens to be all decimal digits (or 0 + all octal digits),
  PyYAML's implicit resolver would read its plain spelling as an int, so the
  validator refuses the file and every later history command exits 1.
  yaml.safe_dump quotes the value, so the file on disk is byte-correct — the
  refusal is a false positive triggered by storing a non-key in a key field.
- Reproduced on Linux, deterministically, in .scratch/repro_fingerprint.py:
  forcing successor_key='213312678452' reproduces the exact CI message and the
  exit code 1. Measured rate over 200k real sha256 fingerprints: 646/200000 =
  0.32% of redactions produce an ambiguous one — so it is a ~1-in-300 random
  event, which is why it looked like a Windows flake and passed on rerun.
- Fix: stop storing a non-key in a key field. Give the removal-set fingerprint
  its own `fingerprint:` field, keep it in the event-id and duplicate-edge
  derivation (third uuid5 component stays `successor_key or fingerprint`, so
  every existing event id is unchanged), and leave `successor_key` to real
  keys only.
