## Decision (justify in PR)

- Chose a WARNING per affected file over extending the duplicate-key ERROR:
  the ERROR is emitted during parse_items, BEFORE any rewrite is even
  planned, so the reporting site cannot know which files a later step will
  repoint. The warning is emitted in loader.load_tree right after the
  rewrite steps have run, from the list of rewrites ACTUALLY applied, so it
  can name files precisely and can honestly say "already on disk". Under
  --no-write all five rewrite steps return [] (loader.py's documented
  invariant), so the warning is silent there -- it can never claim a rewrite
  that did not happen.
- Plumbing: Project.duplicate_id_losses {lost id: (surviving id, collision
  file)} filled by parse._report_duplicate_keys (only for `id:`-key records
  where values differ; the 3-way chain maps every lost id to the LAST value,
  which is what YAML keeps); links.warn_repointed_by_duplicate_key matches
  each applied rewrite whose OLD target is a composite whose display half is
  a lost id and whose NEW display half is the surviving id -- i.e. the
  repoint happened BECAUSE of the collision, not an ordinary rename.

- Implemented: model.Project.duplicate_id_losses (dict, filled by
  parse._report_duplicate_keys for `id:` records only, chained to the LAST
  value so a 3-way repeat maps every lost id to what YAML actually keeps);
  links.warn_repointed_by_duplicate_key (groups applied rewrites by
  (file, old, new), requires old composite display half == a lost id AND
  new display half == the survivor, so an ordinary rename refresh keeps its
  silence); called from loader.load_tree over the concatenation of the four
  rewrite lists, right after the rewrites tally.
