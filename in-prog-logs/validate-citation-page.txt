--------------------------------------------------------------------------------
1. The shape of the fix
--------------------------------------------------------------------------------

**One page grammar, one sentence, one page count.** Three things the tree
already had are now shared instead of copied:

- `citations.page_number(text)` — the picker's `_page_number`, moved to
  `citations.py` and aliased back in `serve/sources.py` as
  `_page_number = citations_mod.page_number` (an alias, not a wrapper, so it
  cannot drift back into a second spelling; a test asserts the identity).
  `serve/api.py`'s inline `?page=` test now calls it too, rather than spelling
  `isascii() and isdigit() and >= 1` a third time.
- `sources.page_absent_message(name, page, count)` — the picker's own
  "page 99 is not in this document -- it has 8 page(s)", extracted so the
  fetch-time warning and the check-time warning are the *same sentence* rather
  than two that drift.
- `citations.page_count(data)` — next to `outline_titles(data)`, both over
  `_pdf_reader(data)` so the missing-extra and unreadable-file wording cannot
  differ between the two questions asked of a document.

**Shape — an error at load** (`build.validate_items`, beside the `keep_copy:`
and `section:` checks, because it needs no file):

```
ERROR   items/cmp.yaml:4 [CMP-001] — datasheets[1]: page: '0' is not a page
        number -- page: must be a positive integer, counted from 1
```

An *unquoted* `page: 4` is a YAML int and is accepted as the number it says —
the JSON Schema types it as a string but nothing enforces that, and refusing it
would be refusing a typo-free line for its quoting. `bool` is excluded
explicitly, since `True` is an `int` in Python and would otherwise read as
`1`. I also fixed `item_specs`' `str(entry.get("page") or "")`, which turned
`page: 0` into *no page at all* rather than page 0 — the one malformed shape
that looked deliberate.

**Range — a page count in the lockfile.** The decision the brief asked for:

> *find out whether the lockfile could or should record the page count at pin
> time so later `check`s don't need to re-open the PDF*

It should and does. `refdes fetch` already opens the PDF for `section:` and it
already downloads the bytes for *every* citation including hash-only remote
ones, so counting the pages costs one `len(reader.pages)` on bytes already in
hand, and the count goes into the record next to the sha256 it belongs to:

```yaml
citations:
  docs/ds-main.pdf:
    bytes: 10393
    fetched: '2026-10-01T09:48:04Z'
    kept_copy: false
    page_count: 8
    sha256: b595f7bdb5a8...
```

Why this and not "open the local PDF during check": `check`/`build` must stay
hermetic and offline (`docs/markdown.md:348-350`,
`docs/cli-reference.md:352-353`), and `refdes[pdf]` is an *optional extra* — a
`check` that started importing pypdf would behave differently on a machine
that has it than on one that doesn't, for a check that has nothing to do with
PDF reading. With the count in the lockfile the range check is pure YAML, runs
with pypdf entirely absent, and costs nothing. A test asserts exactly that
(`test_check_never_opens_the_pdf_to_range_check_a_page`: `page_count` and
`outline_titles` are both booby-trapped to raise and `pypdf` is knocked out of
`sys.modules`, and the warning still appears).

Two more consequences of recording it, both deliberate:

- **It is a fact about the pinned sha, not about the file on disk.** The site
  link is `assets/citations/<sha256>.pdf`, so the count that matters is the one
  for the published bytes — which is also the count for a hash-only remote
  citation whose bytes are no longer on this machine at all. Hence
  `test_a_remote_hash_only_citation_records_its_page_count_too`.
- **It is recorded only for paths that cite a page**, and dropped again when the
  last `page:` for a path goes away, the same rule a resolved section follows
  ("a section that stopped being cited stops being recorded"). Otherwise every
  existing project's lockfile would grow a key on upgrade for citations that
  asked for nothing.

--------------------------------------------------------------------------------
2. The one design change I had to make mid-way, and why
--------------------------------------------------------------------------------

My first cut treated "no `page_count` in the record" as "these pages were never
checked" and warned about it at `check` time. The existing suite caught it
immediately: `tests/test_citation_sections.py::test_page_and_section_disagreement_warns_and_page_wins`
hand-writes a lockfile record (no `page_count`), cites `page: "9"` on a four-page
PDF, and got a second warning it did not expect.

That failure is the real design constraint, and it generalises: **a lockfile
with no `page_count` key does not mean "the pages are unchecked"** — it means
"nobody has claimed anything about the pages", which is true of every lockfile
written by hand and every lockfile written before this change. Treating absence
as a defect would warn about a *lockfile* rather than about a citation, and
would fire once per page-pinned datasheet in every existing project until
someone happened to re-fetch.

So absence is silent, and the two known ways the count can fail to be
established each record *why*, in one key:

```yaml
    page_count_error: 'counting a document''s pages needs the optional PDF extra:
      pip install refdes[pdf]'
```

`page_count` (an int) and `page_count_error` (a clause) are mutually exclusive,
both are recorded only for a path that cites a page, both are written fresh
with the record (nothing carried across a sha change), and both are dropped
when the last page goes. A record with neither claims nothing and is left
alone; every project has to run `refdes fetch` before `check` can pass it, and
that run establishes the count. That is the whole argument, and it is one
sentence in `citations._apply_page`'s docstring.

3. Severity, and how --require-citations interacts
--------------------------------------------------------------------------------

The brief says to match how a `section:` that fails to resolve is treated *in
that docs table*, so I did, and the two new soft rows read exactly like the
`section:` row they sit under:

| condition | `check` | `build --require-citations` |
|---|---|---|
| `page:` not a positive integer | **error, always** (declaration) | error, exit 1 |
| `page:` past the end of the pinned document | warning, per citer | error, exit 1 |
| `page:` never checked (no count recorded, with the reason) | warning, per citer | error, exit 1 |

`--require-citations` escalates both soft rows and promotes neither hard one,
which is the table's existing rule (it exists in `citations.verify` as the
`severity = project.error if require else project.warn` argument every
`_apply_*` already takes).

**Why a warning at `refdes fetch` and not a `FAILED`.** The `section:`
precedent is `FAILED` + nonzero exit, and I deliberately did not copy it,
because the two failures are not the same kind of thing: a failed `section:`
lookup means a *value was dropped* from the record, so the citation is left with
no page at all and `check` reports it as unresolved; a `page:` out of range
leaves the pin and the citation exactly as the author wrote them, and rolling
back a successful pin over a number the author typed would be refusing the
fetch rather than the citation. The pin is the part that succeeded. A second,
practical reason: a datasheet's *printed* page number and its PDF page index
routinely differ by a page, so an off-by-one here is a plausible human reading
rather than a nonsense value — which is exactly what a gate (not a hard stop)
is for. `refdes fetch` prints `WARNING  <path>: page 99 is not in this document
-- it has 8 page(s) (cited by CMP-001)` and exits 0.

**`state` stays `"ok"`, deliberately.** The report noted (P1) that
`docs/output.md`'s `state: "ok"` — "Resolved — hash on file" — is "literally
true and materially misleading here". It is still literally true: the hash *is*
fine. Adding a state value would have meant the state table, both templates, and
`docs/output.md` growing a "the bytes are fine but the page is wrong" case that
no other citation state is about — and `section:` does exactly the same thing
today (wrong page, `state` stays `ok`, the problem goes in `detail`, and the
Detail column renders it). I kept the existing contract and *documented it* in
`docs/output.md`: "`state == "ok"` alone is the claim that the sha256 is right,
which is true and is not the whole sentence."

**A citation whose bytes are not the pinned ones is not range-checked.** If a
local file changed since its pin, `_resolve` has already reported that with the
exact command to fix it, and the recorded count describes bytes the site is not
linking to. Warning "page 99 is not in this document -- it has 8 page(s)" about
a file that now has two pages would be describing a document nobody links.
`test_a_local_file_that_changed_is_reported_as_changed_not_out_of_range` pins
that: exactly one warning, the changed-file one.

`audit` is unchanged and deliberately so: it prints `state`, the pin column and
the citers, and has never printed `detail` for *any* citation problem (an
unresolved `section:` does not show there either). Adding it for `page:` alone
would be a new inconsistency.

4. The pypdf-missing path
--------------------------------------------------------------------------------

The same fallback `section:` documents, at the same moment, in the same words —
`PDF_EXTRA_HINT` is the shared constant, not a second sentence:

- at the pin, a `WARNING`, because the pin genuinely succeeded:
  `WARNING  docs/ds-main.pdf: the pages could not be counted to check the page
  numbers cited here -- counting a document's pages needs the optional PDF
  extra: pip install refdes[pdf]`
- in the lockfile, `page_count_error:` with the same clause, so the fact
  survives
- at `check`, the `section:` row's severity, naming the reason and the command:
  `WARNING items/cmp.yaml:4 [CMP-001] — the page numbers cited for
  docs/ds-main.pdf are not checked: the lockfile records no page count for this
  document because counting a document's pages needs the optional PDF extra:
  pip install refdes[pdf] -- run 'refdes fetch --update --path docs/manual.pdf'
  to establish it`
- and it escalates under `build --require-citations`.

Two fallbacks stay distinguishable, which is the point
(`test_without_the_extra_a_section_citation_still_fails_loudly`): a `section:`
that could not be resolved is a `FAILED` and a nonzero exit (a value was lost),
while a `page:` that could not be *checked* is a warning (no value was lost; the
number is the author's and was not recorded as verified either way).

Unreadable bytes get the same treatment with pypdf's own words —
`counting a document's pages failed: pypdf could not read the PDF: startxref not
found` — and, like `section:`, never a traceback.

One asymmetry worth recording: a plain `refdes fetch` on an **already-pinned**
path does not re-count pages. The recorded count is right there, so it *is*
used to check the pages (`_check_pages` runs in the skip path too — that is the
commonest way a wrong page gets written: an author edits `page:` and runs
fetch), but a path whose record carries no count at all is not nagged about
there. Reporting a non-attempt on every routine re-run would be noise about the
lockfile, and `check` is where the "not checked" row lives.
