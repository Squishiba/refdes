  - `_KNOWN_SETTINGS` derives from those keys, so unknown `on_change` currently fails with
    `unknown setting 'on_change'` (verified with a copied project file).
  - `_validate_settings()` reports unknown settings and special-cases prior renames.
  - `LEGACY_CONFIG_ERROR` names `history:` among settings moved into `refdes-project.yaml`.
  - `load_project()` reads `blocks["history"]["default"]` and uses it as the default per-field

  - `HISTORY_KEYS = {"default"}`.
  - `BlockChecker.history()` validates the `history:` mapping and returns `default`.

### Item-level override

- `src/refdes/parse.py`
  - `RESERVED = {"id", "type", "history", "body", "former_ids", "key"}`.
  - `OVERRIDABLE = {"prefix", "board", "workspace"}`.
  - `_build_item()` reads `raw.get("history")` into `item.history`, validates scalar modes, and

  - The generic loop skips `RESERVED` and handles `OVERRIDABLE` only when the field is not declared.
- `src/refdes/model.py`
  - `Item.history` stores the parsed override.
  - `Item.on_change_for()` implements precedence: item field override, whole-item mode, schema field,

  - `refdes audit` prints `item.history` and help says `item-level history overrides`.

  - `HISTORY_DEF` describes the front-matter override and every type branch unconditionally adds

- `src/refdes/vocabulary.py`
  - `RESERVED_KEYS["history"]` defines the item-key entry and the example writes `history:`.
- `docs/schema-reference.md`, `docs/change-tracking.md`, `docs/authoring.md`, and generated docs

## Verified behavior before changes

- Project-level `on_change:` is unknown today:
  `configuration error: refdes-project.yaml: unknown setting 'on_change'.`
- `refdes revise --help` accepts only top-level mapping sections
  `types:/merge_types:/fields:/links:/prefixes:/citation_keys:`. It cannot rename a setting in
  `refdes-project.yaml`, and it cannot rename a reserved front-matter key. Do not claim revise can
  migrate this rename.

## Decisions

1. Rename both the project setting and item front-matter key to `on_change:`.
2. Old project `history:` becomes a hard configuration error naming the replacement.
3. Old item `history:` becomes a hard item error naming the replacement, except when the item's
   type declares a field literally named `history`; then that field continues to own the key.
4. The new item key must not shadow a declared field. To preserve this guarantee, move
   `on_change` from the strictly reserved family to the overridable family: if the type declares
   field `on_change`, that field owns the front-matter key; otherwise the front-matter key is the
   change-policy override.
5. Rename internal `Item.history` to `Item.on_change_override` so it is not confused with either
   the history store or a field named `on_change`.
6. Preserve value shapes and precedence exactly:
   scalar mode or `{mode, fields, reason}`; item field > item whole > schema field > project default.
