Findings before writing code (all read, not assumed):

- `src/refdes/serve/server.py:283` binds `(security.LOOPBACK_ADDRESS, 0)` with
  the comment "IPv4 loopback only, ephemeral port (0): never a host argument";
  `EditorApp.__init__` takes no port at all, and `_Server` sets
  `allow_reuse_address = False` ("never share a port with a stale listener").
- `cmd_serve` (src/refdes/cli.py:333-352) prints `refdes serve: {app.launch_url}`
  and nothing else carries the token; the only serve flags are `--no-open` plus
  the global `-c/--config` and `--no-write`.
- The token is `secrets.token_urlsafe(32)` (src/refdes/serve/security.py:24-26)
  -- urlsafe base64, so it can contain `-` and `_`. Confirmed the report's point
  is ergonomics, not a live bad regex: grepped src/ and docs/ for token-shaped
  patterns and there is none to fix.
- What a client needs (docs/design/editor-vscode-adapter.md §3.2-3.3): the
  `X-Refdes-Token` header value plus the port. `editors/vscode/serveClient.js`
  `parseLaunchUrl()` already parses exactly `http://127.0.0.1:<port>/?token=<t>`.
  So --token-file writes the full launch URL, not a bare token: one format, the
  one the existing parser eats, and it is self-sufficient even when the port is
  ephemeral.
- House style for a startup refusal: `print(f"error: {exc}", file=sys.stderr)`
  and return 2 (cli.py:1087-1089, 1396-1397, and main()'s SchemaError handler at
  2087-2089). `1` is reserved for "the project has errors", so a bad --port is 2.
- Precedent for file permissions: only `seal.py:219` (`os.chmod(temporary,
  os.stat(path).st_mode & 0o777)`), which preserves an existing file's mode -- no
  0600 precedent exists, so the mode is a decision, not a convention I found.
- Design-doc tension worth naming: docs/design/browser-editor.md:955 says the
  launch token must "never persist or include it in rendered files/logs", and
  editor-vscode-adapter.md §3.2 rejects a token file as option 3. This change
  adds exactly that, as an explicit per-launch opt-in. I am NOT rewriting either
  design doc (dated records); the cli-reference section says plainly that the
  flag is an opt-in deviation and why.

Progress:

- src/refdes/serve/server.py: `EditorApp.__init__` takes `port: int = 0` and
  `token_file: str | None = None`; the `_Server((LOOPBACK_ADDRESS, port), ...)`
  bind is wrapped so an `OSError` becomes `ServeStartupError` with a one-line
  message (`_bind_failure_message`, which special-cases EACCES and EADDRINUSE);
  `self.port` moved inside the try so `launch_url` is available for the token
  file; new `write_launch_file()`; `stop()` and the failed-construction path call
  `_remove_token_file()`. `self.token_file` is assigned only after a successful
  write, so a failed launch can never unlink a path it did not create.

Difficulties / things that bit:

- **A real regression the existing suite caught.** Adding `--token-file` made
  `--token` a valid argparse *abbreviation* of it, so
  `refdes serve --token=<t>` -- which `tests/test_vscode_adapter_contract.py::
  test_launch_url_token_never_appears_in_argv` asserts is refused (design
  §3.2 row 4: no flag may carry a token) -- was accepted and wrote the launch
  URL to a file named after the token, then served forever, so the test hung
  until its 60 s timeout. Fixed with `allow_abbrev=False` on the serve
  subparser; verified `refdes serve --token=abc123` now exits 2 with
  `unrecognized arguments: --token=abc123`.
- A test of my own was wrong first: the relaunch-over-a-stale-file test read the
  stale text because the path already existed, so `_wait_for_file` grew a
  `differs_from` argument.
- `--port 70000` raises `OverflowError`, not `OSError`, in Python, which is why
  the range is checked at parse time rather than at bind().
