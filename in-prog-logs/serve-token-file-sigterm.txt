What N4 says (read from the report, section N4)
------------------------------------------------
`--token-file` exists for scripted use, and the ordinary scripted stop is
`kill $pid` = SIGTERM. `--help` promised the file is "removed when serve stops
cleanly"; the stdout line said "removed on Ctrl+C". Only SIGINT removed it.
Severity low: nothing is lost (the stale file is a valid launch file, rewritten
by the next launch, and its token authenticates nothing once the launch is
gone) -- it is a hygiene issue.

Windows (checked in the docs, not just recalled)
-----------------------------------------------
`signal.SIGTERM` exists on Windows and `signal.signal(SIGTERM, handler)`
succeeds there, but nothing delivers it: `Popen.terminate()`,
`taskkill` and `os.kill(pid, SIGTERM)` all call TerminateProcess, which no
handler intercepts, so a Windows launch cannot clean up after a terminate --
which is exactly why the existing SIGINT test
(tests/test_serve_cli.py:202) is skipped on nt. So the handler is installed only
where it can run, and the new test is skipped on nt with that reason.

What I changed
--------------
1. src/refdes/serve/server.py -- new `sigterm_is_deliverable()` (a predicate,
   False on Windows) and `sigterm_stops_cleanly()`, a context manager that
   registers a SIGTERM handler on entry and puts the previous disposition back
   on exit. The handler raises `KeyboardInterrupt`, so the stop unwinds into the
   `except KeyboardInterrupt` `cmd_serve` already had -> one shutdown path, one
   exit code, no second copy of the teardown ordering. A second SIGTERM while
   teardown is running restores SIG_DFL and re-raises the signal rather than
   raising inside `app.stop()` (which would turn a clean stop into a traceback).
   Registration failures (`ValueError` off the main thread, `OSError` where
   signals are unsupported) fall through to serving without the guarantee
   rather than refusing to run.
   `write_launch_file` is untouched: same temp-file + rename, same symlink and
   foreign-file refusals, same 0600. Nothing about the file's security
   properties moved.
2. src/refdes/cli.py `cmd_serve` -- the `with sigterm_stops_cleanly():` wraps
   `serve_forever()` *and* `app.stop()` (deliberately: a signal landing during
   teardown is still caught). Help text for `--token-file` and both stdout lines
   now say Ctrl+C *or* SIGTERM (`kill $pid`), and that a hard kill cannot be
   caught.
3. docs/cli-reference.md -- the flag table row, the "removes the file when it
   stops on Ctrl+C" paragraph (now: two clean stops, plus the Windows paragraph
   saying why there is no catchable SIGTERM there), and the preview-temp-dir

4. tests/test_serve_cli.py -- `test_token_file_is_removed_when_serve_stops_on_sigterm`

Windows, precisely
-----------------
`signal.SIGTERM` exists on Windows and `signal.signal(SIGTERM, handler)` succeeds
there, but no handler can run for it: `Popen.terminate()`, `taskkill` and
`os.kill(pid, SIGTERM)` all end in TerminateProcess. So no handler is installed
on nt at all (`sigterm_is_deliverable()` is False there and the context manager
yields straight through), a Windows `serve` stopped that way leaves the token
file behind exactly as a hard kill does -- and the next launch rewrites it, the
pre-existing behaviour -- and the new test is skipped there. Nothing on Windows
changes shape: same help text, same stdout, same refusals, same 0600 (the file's
own fchmod guard is untouched).
