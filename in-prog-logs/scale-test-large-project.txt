SHAPE (decided from the docs, not invented)
------------------------------------------
docs/workspaces.md: `item_layout: workspace` => items/<workspace>/<board>/,
board = 2nd segment, workspace = 1st. A `shared: true` workspace may be linked
into without tripping the cross-workspace lint. docs/multi-board.md: boards are
registered with `token:` (checked against id prefix *segments*, per
boards.lint_tokens()), `conforms_to:` per-board coverage obligations against
`group` items whose members point at them with `part_of:`, `includes:` for
shared parts that display but never count.


RESULTS
-------
1. No correctness bug. Coverage accounting is exact at 3,624 items / 12 boards
   / 4 workspaces — every stage count, every per-item stage, every satisfier
   list, every board page, every HTML table matched an independently computed
   ground truth. No report truncation anywhere at this size.
2. One real performance problem, flagged not fixed: boards._find_membership()
   is quadratic in project size once the drift manifest exists. `check` costs
   0.66s before the first `build` and 6.36s after it on the same tree, at
   3,624 items. `refdes keys adopt` makes the same command 0.87s. See
   PERFORMANCE below — this is the thing that decides whether `check` survives
   as a pre-commit command.

PERFORMANCE — the one real finding (flagged, NOT fixed)
-------------------------------------------------------
Wall clock, same machine, this worktree's src:

  items    check(cold, mints keys)   check steady   build    check AFTER build
    280                  0.12s            0.06s      0.39s             0.09s
    961                  0.50s            0.16s      1.49s             0.55s
  3,624                  3.73s            0.66s     11.47s             6.36s

"check steady" is a tree with no .refdes/boards.yaml and no seals; "check AFTER
build" is the same tree one build later. The membership-only part is the
difference: 0.03s, 0.39s, 5.70s. Against item ratios of 3.43x and 3.77x those
are growth factors of 13x and 14.6x — exponent 2.0, clean quadratic.

cProfile of `check` on the built tree (24.1s profiled / 6.2s native):

  boards.py:540  verify                 22.4s of 23.7s   (94%)
  boards.py:463  _verify_membership     22.3s, 2 calls
  boards.py:270  _find_membership       7,248 calls  = 2 passes x 3,624 items
  boards.py:258  _membership_parts      26,042,000 calls = 7,248 x ~3,593

Cause: _find_membership() fast-paths `memberships.get(item.key)`, then falls
through to an unconditional linear scan of the whole manifest looking for a
key-keyed entry whose recorded display id matches. In a project that has never
run `refdes keys adopt` the manifest is keyed by *display id*, so the fast path
always misses and the scan always runs — and can never match, because those
entries are scalars with key=None. Two passes (boards + workspaces) x n items x
n manifest entries.

Confirmed by the workaround, not just by reading: `refdes keys adopt` re-keys
the manifest by surrogate, the fast path starts hitting, and `check` on the
identical built tree goes 6.36s -> 0.87s (7.3x). Build too: 14.78s -> 9.27s.

Projection with k ~= 4.2e-7 s/item^2 (fits all three points): membership
verification alone is ~2s at 2,000 items, ~45s at 10,000, ~4.5 min at 25,000.
So `check` as a pre-commit hook stops being comfortable somewhere around 2-3k
items — and the trigger is the *presence of .refdes/boards.yaml*, i.e. the
normal state of any project that has ever been built and has not adopted keys.
Scoping does not help: `check --board a1` (6.30s) and `check --workspace
product-a` (6.84s) cost the same as the full check, because the whole tree is
loaded and verified before filtering. `ls` is also not cheap at scale (6.3s) —
it runs the same build pipeline with seal_write=False.

Suggested fix shape (deliberately not applied — perf work needs its own scoped
pass per AGENTS.md): hoist the scan out of _find_membership. Build a
{display id -> record id} index once per _verify_membership() call, and skip it
entirely when the manifest section contains no key-keyed entries (the
non-adopted case, where the scan is pure waste). Contained to boards.py, but it
sits in the drift path, so it wants tests of the id-reuse case it exists for.

NOT COVERED
-----------
- Adopted projects at other sizes (only the 3,624-item adopt was measured).
- revision / release / history / serve / calc / parts candidate flows.
- item_layout: board (flat) layout, single-board and legacy projects, projects
  with neither `boards:` nor `workspaces:`.
- The 64 "no board" warnings for shared folders: docs bless unregistered
  shared folders, and the registry here was built from docs/multi-board.md, so
  this reads as intended behaviour, not a bug — but it is 64 warnings of
  noise on a clean project, which is worth a second opinion.
