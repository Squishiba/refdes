## What the code does today

`src/refdes/key_restore.py`:

- `_recorded_current_key` (lines 25-44) already walks *every* baseline, seal
  file, membership manifest and captured-history event, but only to answer one
  question: is the item's **current** key recorded anywhere? That guards the
  opposite direction -- "don't discard a replacement key that history points
  at".
- `apply` (line 75-81) consults it only when `item.key != key`, and only about
  the key being *replaced*.
- Nothing anywhere asks about the key being *restored*: whether the record for
  that key describes the item now holding the display id.

So the F4.2 shape falls through both guards. `_recorded_current_key` returns
`None` immediately when the target item has no key (`if not item.key:
return None`, lines 27-28), which is exactly the new-item case.

## What a baseline stores (read, not assumed)

`lifecycle._items_map` (src/refdes/lifecycle.py:333-336) writes per entry:

    {"hash": item.content_hash, "type": item.type, "title": item.title,
     "hash_format": build_mod.HASH_FORMAT}

plus `key:` in the legacy (display-id-keyed) shape, or `id:` inside the entry
in the adopted (key-keyed) shape. `keys.baseline_identity(record_id, entry)`
reads either shape and returns `(key, display id)` or None for a pre-keys entry
with no identity evidence at all.

So a baseline records **title and content hash**, both directly comparable to
the live item — and `keys.hash_in_format(item, project, format)` is the one
shared reconstruction of "what this item's hash was under the format the record
was written with" (`src/refdes/keys.py:259-277`, used by
`lifecycle.migrate_hash_format`, `seal._matches_sealed_hash` and
`keys.plan_surrogate_storage`). That is the comparison to use, so a genuine
restore of the same item still matches.

Two facts that make the comparison sound:

- An item's **own key and display id are not in its content hash**
  (`build.compute_hashes`'s docstring, src/refdes/build.py:1995-2008), so
  restoring a key onto the item it belonged to leaves its hash untouched.
- `hash_in_format` returns `item.content_hash` for the current format, and
  `load_readonly` does not compute hashes — `adopt.py:218` calls
  `build.compute_hashes(project)` before comparing stored hashes, and so must
  this.

## The fix

`src/refdes/key_restore.py`, one guard plus the plumbing to reach it:

- `_baseline_recording(project, key)` — `(baseline name, recorded display id,
  entry)` for the most recent baseline that filed `key`, or None. Both baseline
  shapes go through the one shared `keys.baseline_identity`, so the legacy
  display-id-keyed entry and the adopted key-keyed entry are found identically;
  `stamped_at` picks the most recent, `name` breaks a tie deterministically.
- `_baseline_content_conflict(project, item, key)` — compares the two signals a
  baseline entry records, `title` and `hash`, against the live item, and returns
  the refusal text if either disagrees. The hash goes through
  `keys.hash_in_format(item, project, recorded_format)`, the single shared
  reconstruction of "what this item's hash was under the recorded format", which
  is what makes a genuine restore of the same item match whatever format wrote
  the record. Absent or unusable signals are skipped rather than guessed at:
  `hash_in_format` returns None for a format this build cannot reconstruct, and
  an entry with neither signal is not a disagreement.
- `apply(..., force: bool = False)` — the guard sits in the same `if item.key !=
  key` branch as the existing recorded-current-key refusal, after it, so the
  pre-existing "would orphan that history" message and its tests are untouched.
  `--force` skips only this guard.
- `build_mod.compute_hashes(project)` after the load: `load_readonly` does not
  compute content hashes, and `hash_in_format` returns `item.content_hash` for
  the current format. `keys adopt` does the same before it compares stored
  hashes.
- `cli.py`: `--force` flag, help text, and the parser description now lists this
  refusal among the others.

Why the *most recent* baseline that recorded the key, rather than the most
recent baseline: a later stamp may not mention the key at all (the item was
gone, or re-issued under a new key), and the newest record that actually
carries identity evidence for it is the one that describes it.

Why refuse on either signal, not both: the title is what a human reads and the
hash is what proves, and they fail independently — a title can be absent from a
record while the hash is there, and vice versa.

Why `--force` is a real override rather than a nudge: the other case that
produces a content difference is legitimate — the same item, edited after the
stamp — and nothing in the project can tell that from a reused display id. The
refusal says so, and the changelog fragment notes that `--force` overrides this
one refusal and nothing else.

| test | what it holds |
|---|---|
| `test_baseline_record_of_different_content_refuses_the_restore` | the refusal: names the key, the baseline, the recorded display id, both differing signals with the recorded and live values, and `--force`; nothing written. | `test_force_overrides_the_baseline_content_refusal` | `--force` end to end through the CLI: refused without it, accepted with it, and the restored key makes the inbound composite resolve again |
| `test_genuine_restore_of_the_same_item_passes_the_baseline_comparison` | the ordinary recovery against a stamped baseline still succeeds — no override asked for |
| `test_same_item_edited_since_the_baseline_needs_force` | the legitimate-difference case: refused, `--force` named in the message, `--force` then accepted |
| `test_restore_is_unchanged_when_no_baseline_records_the_key` | no comparison available, today's behaviour stands. Parametrized: no baselines at all, and a baseline that records REQ-001 with no key in the entry (the pre-keys shape `baseline_identity` returns None for) |

The stamps go through `cli.main(["-c", ..., "revision", name])` rather than a
hand-built project, so the recorded content hashes are real — a comparison
against a `hash: ""` would prove nothing.

## Things worth flagging

- The guard reads *every* baseline's *every* entry on each restore, the same
  walk `_recorded_current_key` already does. A project with many baselines and
  many items pays it twice; if that ever shows up in a profile, both could take
  one index built by `_baseline_indexes` (`src/refdes/lifecycle.py:108`). Not
  done here — it is not a demonstrated problem.
- The refusal compares `Item.title`, which is a derived property (first
  non-empty of `title`/`text`/`summary`/`name`, else the body, truncated at 90
  characters). The baseline records the same property, so the two are directly
  comparable, including the truncation.
- A refusal is possible in a case that is not F4.2 at all: an item whose
  `invalidate` content legitimately changed after the stamp, whose key was then
  lost. `--force` is the answer, and the message names it. That trade is the
  maintainer's decision, not mine; it is one flag away from either answer.
