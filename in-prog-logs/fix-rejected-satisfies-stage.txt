coverage stage? The standard's comment says no; the code says "claimed".
Branch: fix-rejected-satisfies-stage (base main f33efa4).

No code change. The current behaviour (`claimed`) is deliberately pinned by

second branch applies: write up the conflict as a decision for Jared; touch

## 3. Decision (per task step 3, branch two)

Sources do NOT disagree -- base.yaml's "never satisfies", the design doc,
the test, and both docs pages all mean: a rejected satisfier never closes
coverage (never `satisfied`); its link is recorded as `claimed`. The probe
observation is a wording ambiguity in the base.yaml comment (it can be read
as "counts for nothing"), not a code/docs conflict. The comment is not
plainly the stale side -- it is quoted verbatim by the design that owns it
-- so it is left alone, per the task's instruction to fix it only if plainly
stale. For Jared: if "a dead-status claim should count for nothing (stage
falls past `claimed` to open/addressed)" is wanted, that is a new third
bucket in the settled/claimed model (_coverage_for, build.py:1136-1139), a
docs change (coverage.md/concepts.md stage tables), a base.yaml comment
change, and a deliberate reversal of test_rejected_never_satisfies -- i.e.
a design decision, not a bug fix. That is exactly why no code was touched.
