# item-on-change-mapping-validation

Task: an item's `on_change:` MAPPING form must be validated like its scalar
form (run 6b finding B2, PR #222 report). Branch cut from main f7df34d.

## Reproduction (BEFORE fix) — confirmed, hardware@3, `refdes init` in

`refdes check` (pre-fix): `3 items, 0 errors, 4 warnings`, exit 0 —

## Fix (src/refdes/parse.py, `_apply_change_override`)

- `mode:` value validated against ON_CHANGE_MODES (the legacy `log`
  branch kept first, so its rename message is unchanged); bad mode ->
  `on_change mode: 'x' must be one of invalidate, timeline, ignore`.
- every `fields.<name>:` value validated the same way (legacy branch kept
  first); `on_change fields.<name>: 'x' must be one of invalidate,
  timeline, ignore`.
- unknown keys inside the mapping (e.g. `mdoe:`) were NOT reported (the
  emitted schema.json declares `additionalProperties: False` for the
  mapping, so this is the same class); added
  `on_change: unknown key 'x' -- must be one of fields, mode, reason`.
  Fit inside ~20 added lines, so included per the task.
- Drop-vs-keep decision: the scalar form DROPS the invalid value (errors
  and returns without setting the override). The mapping drops only the
  offending entry (`del override["mode"]` / `del fields[fname]` /
  `del override[key]`), keeping valid siblings — entry-granular version of
  the same "drop, don't apply" policy. Consumers (model.py:673-678,
  cli.py:1474-1482) all read via `.get()`, so a dropped key falls back to
  schema field mode / project default, exactly like the absent-key case.
- After fix, the repro project: 4 errors, exit 1, one per case, scalar
  message unchanged.
- NOT touched (out of scope, noted only): non-dict `fields:` (e.g.
  `fields: ignore`) is still silently ignored — the task scoped this to
  mode values + unknown keys, and the suite/contract tests keep the
  legacy-log precedence intact.
