What #182 literally names is stale on main. The claim:
`_LockfileWrite.rollback` reads the lockfile, compares, and restores with
no lock, so a cooperating writer landing in the compare->restore gap is
overwritten by our `previous`. That gap is closed on main: read, compare
and restore are one `project_write_lock` section (PR #195 follow-up,
commit d804b59), and `tests/test_citations_lockfile_locking.py::
test_no_writer_lands_between_the_rollbacks_read_and_its_restore` proves
it with a thread that cannot get the lock. T3 evidence: that committed
test, green on main.

What is NOT closed on main is the family #182 belongs to (the same
write-before-gate shape), and the deterministic probes added to
tests/test_serve_sources_accept.py prove it red on origin/main:

  it is the regression guard for the merge-landing rule.

Why a predicate cannot fix it (decided the HOLD-vs-fix question): at
refusal time, the clobber's disk state is BYTE-IDENTICAL to the state of
a refusal that REQUIRES the restore (a pre-named pair pinned by nothing;
deleting our pin is mandatory there). No observation of shared disk state
separates the two worlds. A file-mtime predicate is FS-granularity
dependent (FAT/NFS second granularity), i.e. not sound. So #240's
tree-check guard was rejected on its P1 hole (an added same-line body
edit escapes the multiset), and the fix removes the window instead of
watching it.

The fix (this branch):
- model.Project gains `lockfile_overlay`; citations.load_lockfile reads it
  when set (overlay posture, like source_overlay; overlay loads are
  read-only, load_tree raises on write=True).
- loader.load_tree/load_readonly gain `lockfile_overlay=`.
- serve/edit.py: `_accept_pins` no longer writes. It stages whole-file
  bytes in memory under the project lock. The gate judges the candidate
  via `lockfile_overlay`. The final section lands the PAIR: revision
  check -> `_land_lockfile` (skip-if-equal / write-if-unchanged /
  re-stage-merge over fresh records under fetch's policy if a cooperator
  moved the file; "already pinned by someone else" -> skip write, land
  body) -> body replace; on body-replace failure `_restore_lockfile`
  puts back what THIS section's write replaced, under the same lock
  (seconds, not a window). `_LockfileWrite`, `rollback()`, `_undo_accept`
  and all five of its call sites are gone.
- docs/design/editor-source-picker.md §4 rewritten: new sequence, the
  indistinguishability proof, the re-stage rule, and the honest residue
  (crash between the two replaces -> inert pin, cleaned by fetch;
  writers that ignore the lock are not serialisable by anything here).

Test topology note: the old locking test fired the writer thread inside
`_rollback`, reached by a gate failure after the write. There is no
write before the gate any more, so that test is rewritten to fire the
writer at the one surviving restore site: the body's `_atomic_replace`
failing after the lockfile landed. Same guarantee, same probe style
(events, not sleeps; the writer asserts it CANNOT have landed).
The test_serve_sources_accept seams that simulated "failure after the
lockfile landed" now simulate failure inside the read-only gate; their
assertions (both files byte-identical on refusal) got STRONGER for free:
with nothing written before the gate, refusal leaves nothing by
construction, and the tests still prove it.

All three verms: CHANGES REQUESTED. The one that mattered: a4e70e13
rated it LOW/out-of-scope, but it is a gate-approval violation and the
round's brief said fix-if-real. It is real, reproduced by probe:

  - The landing section's "file stands" branch fires when the moved

  - Same hole in the merge branch: the re-extraction runs against the
    co-actor's records, so a key can extract at a value the gate was
    not judged on, and the drifted pair lands.

Fix (src/refdes/serve/edit.py, _land_lockfile): the section now
carries `expected`, the (path, key) -> value map from the accept's
read. "File stands" requires the pin AT the expected value; a pair
pinned to a different value is a refusal naming both values. After
the merge re-stage, every re-extracted pin is checked against
`expected` the same way; drift is a refusal. Both refusals return
before any write, and both name the repair (re-accept against the
current lockfile). This also resolves a4e70e13's L4: a refusal no
longer echoes a stale `pinned` list, because drifted pairs are
refused before the response is built.
