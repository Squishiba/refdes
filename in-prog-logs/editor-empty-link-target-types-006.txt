## Finding, verified

`src/refdes/serve/static/links.js` `candidatesFor(types)` built one
`/api/items?type=` query per declared target type. For a verb declared
with `target_types: []` it issued no request at all, the picker rendered
"no candidates match", and the author could not add a link that the server
freely accepts.

The server reads an empty list as UNRESTRICTED in three places, all
consistent (verified by reading, file:line cited):

- `model.py:1143` `Project.accepts_type` — docstring: "an empty list is
  unrestricted"; returns True when `allowed` is falsy.
- `build.py:911` `resolve_links` — the type check runs `if allowed and ...`,
  so an empty list skips it.
- `serve/edit.py:795` `_resolve_link_op` — gates adds through
  `accepts_type`; its refusal message for the non-empty case is "targets of
  type X", and model's docstring phrasing for the empty case is "any
  declared type".

Real-world case in the bundled standard (hardware@3):
`src/refdes/standards/hardware/v3/base.yaml` — `log.links.blocked_by: []`.

Live HTTP probe (`.scratch/editor-empty-target-types/probe.py`, run with
this worktree's src on sys.path, real `EditorApp` on a temp project):

- `GET /api/item/LOG-001` reported
  `blocked_by: {editable: true, target_types: [], targets: []}`.
- `POST /api/item/LOG-001/edit` with
  `{op: add_link, verb: blocked_by, target: REQ-001}` → 200 `applied`,
  wrote `blocked_by: REQ-001@gchz7enm6r9` (the composite) to items/log.yaml.

So: server accepts, picker offers nothing. The narrow seam is JS-only.

## Fix

links.js `candidatesFor`: empty declared list → fetch the unfiltered
`/api/items`; declared types → unchanged per-type queries. Header comment
and a block comment say why, naming the three server-side readings. No
Python touched (edit.py avoided per the active-PR note: #240/#241/#244/#253).
