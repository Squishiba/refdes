## Severity decision for F7 (not by feel)

Docs, in the repo, for the same class of mistake at top level:
- `docs/authoring.md:267-292` — "An unknown field whose spelling is close to
  one the type declares is a build **error**" ... "An unknown field with
  nothing close to it stays a **warning**, and the value is kept:
  forward-compatible metadata, a field a future schema version will declare,
  deliberate extra data."
- `docs/troubleshooting.md:103-109` — same two-tier rule.
- `src/refdes/parse.py:965-992` — the implementation of that rule
  (difflib cutoff 0.6 → error, else warning + value kept).
- `docs/design/backlog.md:1553-1558` — the asymmetry principle: an unvalidated
  sub-key is "the whole difference between a typo doing nothing and a typo
  doing the wrong thing".

The report's own framing: "Top-level unknown fields *are* warned about; the
gap is only in list-entry sub-mappings." So parity = the two-tier rule, and
the report's example key (`exrta`) has nothing close to `value`/`against` →
**warning**, not error. Note the near-miss case is already an error today by a
different route: typo'ing `value:` itself trips run_checks' existing
"each checks: entry needs 'value' and 'against'" error, so the only newly
reported shape is an *extra* key beside a valid pair — the docs'
"deliberate extra data" case, which they keep at warning.

## One crash found on the way, and what I did about it

Writing the F7 loop I had to ask what a *non-string* key inside a `checks:`
entry does, because YAML reads `true:` as the bool and `1:` as the int: my
`sorted(entry)` would compare `bool` against `str` and raise, one step earlier
than anything else in the run. So the loop sorts with `key=str` and formats
with `str(key)`, and
`test_a_non_string_key_crashes_where_it_already_did_not_in_the_new_loop` pins
the frame the `TypeError` comes from.

The `TypeError` itself is **pre-existing and not fixed here**: a `checks:`
entry with a `true:` key already dies inside `compute_hashes` →
`json.dumps(payload, sort_keys=True)` (`build.py:1769`), which is hashing code
this branch does not touch. Verified against an unmodified source tree
(`/home/jorb/work/refdes`, `.scratch/probe_prechange.py` → `RAISED TypeError
'<' not supported between instances of 'bool' and 'str'`), so it is not a
regression I introduced and not in F4/F5/F7's scope. Worth its own finding:
it is the same family as B1 — a shape the loader accepts and a later stage
cannot serialize — and unlike B1 it is not even a diagnostic, it is a raw
traceback out of `refdes check`.
