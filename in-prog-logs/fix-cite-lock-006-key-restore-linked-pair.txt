Reproduced in both argument orders, with the composite link (`REQ-001@k1` →

same item, edited since that baseline was stamped").

## Mechanism

`apply` ran `_baseline_content_conflict` on the live pre-restore project
(hashes computed at the top via `build.compute_hashes(project)`). An item's
content hash embeds its links' *resolved target keys* (build.py
`_link_hash_token`, keys.md §5), so the owner's pre-restore hash sees the
keyless target as a sentinel, not its lost key — a mismatch the baseline
reads as moved content. The target's own hash is key-independent, which is
why target-first-then-owner as two commands always worked.

## Fix (src/refdes/key_restore.py)

The baseline comparison moved to run on the *candidate* — the project loaded
from the in-memory overlay of all planned key restores, after the
blocking-errors check — so it judges the proposed post-restore state: in a
pair batch the target already carries its restored key. Genuine conflicts
are untouched: content/title genuinely moved (either half), target key lost
and NOT in the batch (sentinel stands in post-restore too), reused display
id — all still refused, and nothing is written on refusal. `--force` skips
the comparison as before. The now-unneeded `compute_hashes` on the live
project is gone; it runs on the candidate (inside `not force`).
