## F1. test_serve_cli stale-token test flakes under parallel load — cause found, test fixed

- What it waits on: `_wait_for_file(token_file, differs_from=stale)`, 60s
  wall-clock deadline, polling the *file* every 50ms. The file appears only
  when the second `refdes serve` child process gets through its whole startup
  chain: Popen -> CPython interpreter start -> `import refdes.cli` (+yaml) ->
  `EditorApp.__init__` -> `ProjectState.load()` -> `_build()` = full
  read-only project load *plus* `preview.render(project)` (the whole site
  rendered to a temp preview dir) -> socket bind -> `write_launch_file`
  (src/refdes/serve/server.py:464-465). The deadline starts when Popen
  returns, so the 60s covers the entire cold start of a CPU-bound child.
- Why load starves it: with ~6 pytest suites (each also spawning refdes
  subprocesses) on one box, interpreter start + import + load + full render
  can exceed 60s purely on CPU/IO contention. On an idle box the whole test
  is ~2s. Nothing in serve blocks; the ordering (load before bind/write) is
  deliberate -- a project that fails to load must not bind a port or publish
  a credential (see cmd_serve's exit-2 refusal posture and
  test_serve_on_a_directory_without_a_project_exits_with_an_error). So not a
  code bug; the fixed 60s wall for a child cold start is the test's problem.
- Fix: raise `_wait_for_file`'s timeout to 180s with a comment naming the
  chain it covers. Ran the test alone 5x (results below).
