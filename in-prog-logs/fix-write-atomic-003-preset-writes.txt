Regression found (review of commit 1a9ca20)
-------------------------------------------
The atomic-write switch regressed symlinked configs. textio.atomic_write_text
ends in `os.replace(tmp, path)` (src/refdes/textio.py:298); `rename(2)`
replaces the *symlink itself* with the regular temp file rather than following
it. The truncate-on-open textio.write_text it replaced used open(path, "w"),
which DID follow the link. So for a project whose refdes-project.yaml is a
symlink to actual-project.yaml in the same directory, add-preset/remove-preset
now replaced the symlink with a regular file and left actual-project.yaml
untouched — it lost the symlink and edited the wrong (new) file. The ENOSPC
protection, mode preservation and clean refusal the fix added were still fine;
only the symlink path regressed.

Reproduction (.scratch/review_atomic_symlink/probe.py, run against this
worktree's src with PYTHONPATH=<worktree>/src, refdes.__file__ checked):
  baseline @8b6a52e : marker_symlink True,  target_changed True, marker_has_preset True
  branch   @1a9ca20 : marker_symlink False, target_changed False, marker_has_preset True

Fix (narrow, call-site)
-----------------------
src/refdes/scaffold.py: added _config_write_target(config_path) returning
os.path.realpath(config_path), and pointed the two REAL config writes (add_preset
and the remove_preset final write) at it. The remove-preset scratch simulation
copy is deliberately NOT resolved — it is an ephemeral regular file next to the
marker, written and removed by name.
  - os.replace then lands on the resolved real file, so the symlink keeps
    pointing at it and the bytes go behind the link (rename replaces the file,
    the link is by name so it still resolves).
  - For an ordinary (non-symlink) config realpath is just the absolute path:
    same directory (temp created there), same basename (temp prefix), same
    mode (os.stat). No-op for the common case — verified by the pre-existing
    atomicity/mode/refusal tests still passing.

Why narrow and not textio.atomic_write_text
--------------------------------------------
atomic_write_text is shared with ids.py (id-ledger write) and revise.py (source
rewrites + rollback). Changing its rename semantics there would alter two
untested-by-this-issue writers at once and its own read-only/dir checks. The
task said a narrow call-site resolution of the real config target may be
better; the evidence (blast radius + the realpath no-op for non-symlinks)
supports the call-site fix. atomic_write_text is left unchanged.
