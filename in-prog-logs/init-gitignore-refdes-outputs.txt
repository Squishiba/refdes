times that `.refdes/copies/` and `.refdes/schema.json` are gitignored; the

## Pattern choice — checked, not assumed

No leading `/`. Each pattern contains a slash away from its end, so
gitignore(5) resolves it relative to the directory holding the `.gitignore`
— which is what a `.gitignore` `init` writes at the project root needs in both
layouts. Verified with `git check-ignore -v` in a scratch repo
(`.scratch/pattern-check`, `.scratch/roundtrip`), both for a project at a repo
root and one at `repo/hardware/board-a`:

```
.gitignore:13:.refdes/copies/      .refdes/copies/x.pdf
.gitignore:18:.refdes/schema.json  .refdes/schema.json
nested/proj/.gitignore:18:.refdes/schema.json  nested/proj/.refdes/schema.json
```

and `.refdes/ids.yaml` still NOT ignored in both, `.vscode/tasks.json` still
not ignored, and `nested/.refdes/copies/b.pdf` (a *different* project inside the
same repo) NOT ignored — which is right: each project ignores its own.

Also verified end to end: after `init` + `refdes check` in both layouts,
`git add -A` stages `.gitignore`, `.refdes/ids.yaml` and `refdes-project.yaml`
only. No datasheet copy, no `schema.json`.

## Difficulties

- The CLI announcement could have come from `init`'s return value, but ~30
  tests and the module's documented contract pin that to the config path. Read
  `.gitignore` before/after in `cmd_init` instead and diff it with a pure
  helper; that also makes "wrote" honest — a project whose `.gitignore` already
  covered everything gets no line rather than a line claiming a write that did
  not happen.
- Deciding whether the `.refdes/` entries should depend on
  `write_vscode_settings` was the one real judgement call. They should not:
  `build`/`check`/`fetch` create those files regardless of what happened to the
  editor settings. That changed one test's premise (it asserted *no*
  `.gitignore` at all), which is why it is renamed and its docstring rewritten
  rather than quietly deleted.
