## 2. The URL mapping (verified, not assumed)

`.github/workflows/docs.yml` runs `refdes build` in `docs-site/` and uploads
`docs-site/../_docs` — i.e. the repo-root `_docs/`, which `.gitignore` keeps
out of the tree. `docs-site/refdes-project.yaml` sets `site.out: ../_docs` and
`site.pages: ../docs`, so **every** `.md` under `docs/` is a page in that build.

I ran the build locally (from `docs-site/`, with
`PYTHONPATH=<worktree>/src python -m refdes.cli build`) and listed
`_docs/**/*.html` to see the real filenames rather than guess them. Two things
came out of that:

- A top-level `docs/<page>.md` renders to `<page>.html`, matching the existing
  `DOCS_URL` use in `cmd_init` (`{DOCS_URL}/parts.html#...`).
- **`docs/design/*.md` are published too, but flattened**: `docs/design/keys.md`
  becomes `design-keys.html`, not `design/keys.html`. They also appear in the
  rendered nav (`_docs/index.html` links `design-keys.html` and 25 siblings),
  because `site.nav:`'s own comment says "Anything not listed falls in after
  these, alphabetically."

So a `docs/design/keys.md` URL *would* resolve — `design-keys.html` exists in
the build. I still did not use it, for two reasons: it is a design doc aimed at
contributors, not the user docs a person chasing a lost key wants, and the task
says to point at the nearest *published user-facing* page for the same topic.

Page chosen for the four `docs/design/keys.md` pointers:
**`troubleshooting.html#surrogate-keys`** (`docs_url.SURROGATE_KEYS_DOCS`). That
page's own nav has a top-level `## Surrogate keys` section — verified as
`id="surrogate-keys"` in `_docs/troubleshooting.html` — and it is the page the
docs already cross-link to for exactly this material (`docs/multi-board.md`
points readers at `troubleshooting.md#surrogate-keys` for the imported-lost-key
case). It covers composite form, `refdes keys restore`, and the "why is a
composite I never typed failing" question, which is what all four messages are
answering.

Pages for the other two, direct 1:1 mappings, both verified present in the
build: `_docs/multi-board.html` and `_docs/workspaces.html`.

Anchor scheme, confirmed against the one URL already in the tree: heading text
lowercased, non-alphanumerics collapsed to `-` — `### Candidate parts: the
recommended layout` becomes `id="candidate-parts-the-recommended-layout"`, which
is exactly the fragment `cmd_init` uses. Backticks around a heading (`## \`refdes
keys restore\``) become plain hyphens: `id="refdes-keys-restore"`.

Verification of all three URLs, twice over. `.scratch/verify_docs_urls.py` builds
`docs-site/` and then, for each constant, asserts (a) the `.html` is in `_docs/`,
(b) the fragment, if any, is a real `id=` in that page, and (c) the page is
`href`-linked from the rendered nav on `index.html` so it is reachable rather
than merely present. It runs `parts.html#candidate-parts-the-recommended-layout`
as a control on the anchor scheme. Result: no failures. Against the **live**
site: `curl` gives HTTP 200 for `troubleshooting.html`, `multi-board.html` and
`workspaces.html`, and the deployed `troubleshooting.html` really does carry
`id="surrogate-keys"`.

Note `pyproject.toml`'s `[project.urls] Documentation` is the same base URL, so
`DOCS_URL` has a second, independent source of truth agreeing with it.


## 4. Where DOCS_URL lives now

New `src/refdes/docs_url.py`: the base URL, its comment (moved there whole), and
one named constant per page the diagnostics point at, so the page-to-URL mapping
is in one file rather than spelled out at each call site.
`build.py`, `keys.py`, `links.py` and `configcheck.py` each `from . import docs_url
as docs_url_mod`; none of them imports `cli`, so there is no cycle. `cli` imports
it and does `DOCS_URL = docs_url_mod.DOCS_URL`, so `from refdes.cli import
DOCS_URL` keeps working for `cmd_init` and for anything else importing it.

Verified by importing each of `refdes.build`, `refdes.keys`, `refdes.links`,
`refdes.configcheck`, `refdes.docs_url`, `refdes.cli` standalone in a fresh
interpreter (a cycle would blow up on the first of them), and by asserting
`cli.DOCS_URL is docs_url.DOCS_URL`.

Note on naming: the log above first wrote the constant name as `DOCS_SURROGATE_KEYS`;
the shipped name is `SURROGATE_KEYS_DOCS`, matching `MULTI_BOARD_DOCS` /
`WORKSPACES_DOCS` so the three read as one set.
