# run-5 F3 — the opt-back-in overlay must report itself

Task: `types: log: sealing: build` in `refdes-schema.yaml` switches an
append-only type from history-backed to build-sealed, and `check`/`build` print
nothing about it. Add a diagnostic naming the type and the overlay file, at the
severity the report asks for, without changing exit codes.

## Reading the finding

`in-prog-logs/user-sim-release-gate-run5.md`:
- §F3 (line 564): "There is no `note:`, no `WARNING`, nothing confirming the
  overlay resolved. A user who adds it and runs `check` cannot tell whether it
  worked, and a user whose *intent* was the overlay but who forgot it has no
  way to discover that either."
- Findings table (line 104): severity **friction (low)**, surface `check`,
  `build`.
- §5 table (line 449): the overlay "works, silent (F3)"; the typo'd value and
  the wrong-file cases already exit 2 with good messages — only "took effect"
  is unreported.

## Severity decision (from the report, not from feel)

`note:` on stderr, not a WARNING and not a `project.info()` diagnostic.
- F3 is graded friction (low) and the overlay is a *deliberate* decision, so it
  owes the reader no severity. Run-5 B4 in the same report is precisely the
  complaint that a second diagnostic on one condition inflates
  `N errors, M warnings`; a standing warning about a decision the author just
  made would do that on every run of every project that has the overlay.
- `project.info()` was rejected because `_visible()` (cli.py) hides info
  diagnostics unless `--verbose` — the author would still be unable to see that
  the overlay took effect, which is the whole finding.
- Exit codes: `_report()` returns `1 if errors else 0`, so a stderr note joins
  no count and moves no code. Verified by test and by hand (below).

## What changed

- `standards.build_sealing_optins(base_types, project_types_raw, resolved_types)`
  — the detection. A type counts only if (a) the project's own overlay sets
  `sealing: build` for it, (b) the standard (base+presets) had it on something
  else, and (c) the resolved spec is still `append_only`. (b) is why the check
  lives in `standards.py`: it is the one place the standard's own value and the
  project's override are both in hand. (a) is safe because `load_project`
  merges `refdes-project.yaml` and the overlay only after validating that
  `types:` can come from the overlay file alone, so an overlay `types:` block
  is always `refdes-schema.yaml`'s. (c) keeps a project that switched the type
  off append-only out of it — sealing only names what backs an append-only
  type's guarantee, per schema.py's own rule.
- `resolve_namespaces` returns a 5th value, `sealing_optins`; `resolve_schema`
  (the 2-value form, used by tests) is unchanged in signature.
- `Project.sealing_optins: list[str]` (model.py), filled by `load_project`.
- `cli._sealing_optin_note()` + `_announce_sealing_optin()`, called from
  `cmd_check` and `cmd_build` only — the two commands F3 names.
- `docs/design-log.md`: the overlay paragraph now quotes the line.
- `changelog.d/sealing-optin-overlay-note.added.md`.

The note:

    note: refdes-schema.yaml opts the 'log' type back into build sealing -- an
    edit to a sealed entry is a build error again, not the history-backed
    'edited after captured' warning

(one line; wrapped here for the log). Multi-type form: "opts 2 types (a, b)
back into build sealing".

## Left undone / uncertain

- Only `check` and `build` print it, because that is what F3 names. `release`,
  `audit`, `revision` and `index` load the same project and stay silent; if the
  note should be project-wide, the place is `_report()`, and that would also
  put it in front of `index`'s JSON on stdout (it goes to stderr, so it would
  not break it) — a wider call than this finding.
- Read-only modes print it too, which is right (it is a schema fact, not a
  write) and is now verified by hand rather than assumed: `refdes --no-write
  -c cfg check` and `refdes build --dry-run` both print the note and exit 0.
  `refdes ls` and `refdes index` print no note (index's stdout is still clean
  JSON). Not covered by the test file — the two commands F3 names are.
- The `append_only: false` skip is tested at the detection level
  (`sealing_optins == []`) and by silence, but it is a negative test, so like
  the other silence tests it cannot fail against the pre-change tree except
  through the missing `Project.sealing_optins` attribute. The regression
  evidence is the positive tests: 9 of the first 10 failed before the change.
- Stray file: `in-prog-logs/in-prog-logs-run5-f3-overlay-note.txt` is an early
  draft of this log written before I registered the required filename. This
  environment has no file deletion, so it is left in place, unmodified-and
