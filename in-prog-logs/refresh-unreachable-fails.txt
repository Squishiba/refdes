Three facts that settle the classification question (§3):
a. an HTTP error status already lands in the *same* bucket as connection
   refused — the `except Exception` at citations.py:2469 — and is reported as
   "could not refresh", never as drift;
b. plain `fetch` treats it as a hard **failure** (exit 1), not as a changed
   document;
c. a 302 is followed inside `fetch_bytes`' `urlopen`
   (`src/refdes/citations.py:949-954`) before any hashing, so the redirect case
   is indistinguishable from a direct 200 and is compared/pinned on the final
   bytes — in `refresh` and in `fetch` alike.
## 2. The decision, and why the flag is named that

Flag: **`check --allow-unreachable`** (`citations.ALLOW_UNREACHABLE_FLAG`, read by
`cli.py` when it registers the argument, so the string in the diagnostic and the
string on the command line cannot drift apart).

Naming checked against the other `check` flags (`--refresh`, `--board`,
`--workspace`, `--verbose`) and against `build`'s (`--keep-going`,
`--require-citations`): all lowercase, no abbreviation, either a report filter or
a named posture. Candidates rejected:

- `--strict-refresh` — the shape the exercise itself proposed (F4, "a better fix
  is an `--strict-refresh` that escalates unreachable to an error, opt-in for
  CI"). It is wrong now: the escalation is the *default*, and the flag is the way
  back out. Naming it "strict" would also imply the un-flagged run is lax, when
  the un-flagged run is the one that fails.
- `--ignore-unreachable` — true-ish, but `--ignore` reads as "do not report",
  and this reports either way, as a warning.
- `--refresh-best-effort` — vaguer about what is given up, and `--refresh` is
  already required for it to mean anything.

`--allow-unreachable` says the one thing the flag does, and its `--help` spends
its second sentence on what you give up, which is the half that matters.

## 3. Classification: HTTP error statuses and redirects (the judgement call)

**Decision: an HTTP error status is "unreachable", not a finding. A redirect is
neither — it is not visible to the refresh path at all.**

Justification, all three points verified on main before the change (§1):

1. *That is the bucket it is already in.* `refresh()` wraps the fetch in
   `except Exception` and reports "could not refresh", so a `404` and a refused
   socket have always produced the same diagnostic
   (`citations.py:2469` pre-change; reproduced in §1's status probe). Promoting
   4xx/5xx to a *finding* would be a second, larger change — a new class of
   "finding" that no severity table, `audit` state, or `build
   --require-citations` counterpart knows about — and the brief says not to
   change classification beyond what this decision needs. Keeping 4xx/5xx as
   unreachable means the exit code changes for them (0 → 1, or 0 with the flag),
   which is exactly the change the maintainer asked for, and nothing else does.

2. *It is what plain `fetch` already does, so this is the consistent choice.*
   `fetch --update` against the same 404 printed `FAILED … HTTP Error 404` and
   exited **1** (§1). A deleted datasheet is a failed fetch in the one command
   that fetches for a living; it should not be a quiet success in the one that
   only compares. After this change both exit 1 on a 404, and both are silenced
   the same way — for `fetch` by not running it, for `--refresh` by
   `--allow-unreachable`. Conversely, calling a 404 *drift* would be new
   territory: drift means bytes arrived and differ, which is precisely what the
   pre-existing docstring said and why.

3. *Redirects cannot be classified differently without inventing new
   behaviour.* `fetch_bytes` is one `urlopen` call
   (`citations.py:1635-1640` on current main; the exercise quotes 949-954, from
   before the file grew), and `urlopen` follows 3xx itself. By the time the
   fetcher returns, a 302 that landed on a 200 is indistinguishable from a
   direct 200, and its final bytes are what gets hashed and compared — the same
   bytes `fetch_all` pins. So a working redirect already behaves correctly
   (§1's probe: it compared and reported drift, exit 1), and a redirect that
   ends in an error status, exceeds urllib's redirect cap, or loops raises
   `HTTPError`/`TooManyRedirects` and lands in the unreachable bucket with
   everything else. **No redirect-specific diagnostic was added**: the refresh
   path never sees the hop, `fetch` never reports one, and inventing a "redirected
   to" note here would be a new feature, not a fix.

## 5. Implementation shape

- `citations.refresh(project, fetcher=None, allow_unreachable=False)`. The
  unreachable branch keeps today's per-url message verbatim on the bypass path
  (so anything grepping for `could not refresh <url>` still works) and adds the
  "NOT verified" tail plus a one-line summary on the strict path. The summary
  names the flag, because an error with no remedy sends the user to the docs
  mid-incident. It is emitted through `project.error`/`project.warn` rather than
  printed directly, so it gets the `ERROR`/`WARNING <project> — ` prefix, lands
  on stderr, and is counted in the `N items, N errors, N warnings` line — which
  is what makes a CI filter looking for `ERROR` see this failure at all (F4's
  complaint).
- `cli.cmd_check` passes the flag through, and prints the no-op note when
  `--allow-unreachable` arrives without `--refresh` — the same shape as
  `build`'s existing `--no-write -- --reseal` note (`cli.py:332`).
- Drift handling is untouched: same block, same `status = 1`.

  row now says it fails the run), the drift section (real captured failure and
  bypass output, what you give up, partial outages, redirect/status rule), and
  the exit-code preamble at the top — a script branching on `1` now needs to know
  that code can mean "nothing was checked".
- `docs/markdown.md` (citing a datasheet), `docs/troubleshooting.md` (new
  diagnostic entry, splitting network failure from a 404, with the remedy for
  each). Both pages grep-verified as the only other places discussing
  `--refresh`.
- `changelog.d/check-refresh-unreachable.breaking.md`.

**Breaking, deliberately.** `changelog.d/README.md`: *breaking — existing
projects must change*. A workflow running `refdes check --refresh` now fails
where it passed, and it must be changed *by a person* — accept the new exit code
or pass `--allow-unreachable`. `changed` would be a lie (a green CI job that
went red is not a behaviour tweak), and `fixed` would hide that from anyone
upgrading. The precedent is `citation-page-checked.breaking.md`, which called the
one new failure an upgrading project meets breaking for the same reason.
