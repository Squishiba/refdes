Review on cc2e5be: _umask_respecting_mode() mutated the process-wide umask
(set-and-restore); any concurrent thread creating files in the window gets a
wrong mode, and the "serve never seals" claim shouldn't be load-bearing.
Re-audited callers to test that claim: seal_write=True reaches seal.verify
only through cli.py:403 (the build command); every other build() call site
(serve/edit.py:358, loader.py:193, revise.py:1384, cli check/index/ls/...)
is seal_write=False; revise.py:2038 calls save_seals directly. All CLI. But
the design should not depend on that, so it was replaced.

Options considered:
- Keep NamedTemporaryFile + a separate same-directory O_CREAT|O_EXCL mode-0666
  probe file: works but adds a second file, its own collision handling and a
  crash-debris class, for information the temp creation itself can produce.
- mkstemp/NamedTemporaryFile then chmod from a computed mode: back to reading
  the umask somehow. Rejected.
- Chosen: create the seal temp itself with os.open(O_WRONLY|O_CREAT|O_EXCL,
  0o666) -- the kernel filters the creation mode through the umask, so a NEW
  seal file lands 0666 & ~umask with no chmod, no probe, no process-umask
  mutation; the existing-file branch still copies the old mode verbatim.
  Same-directory creation is already required for the os.replace to be
  atomic, and it is the repo's own idiom (serve/edit.py _atomic_create opens
  its temp at 0o666); the random name uses secrets.token_hex like keys.py /
  serve/security.py. Uniqueness via O_EXCL + retry loop (mkstemp does the
  same). tempfile import dropped.

Trade-off accepted: the temp is group-readable while being written under a
group umask (the old temp was 0600 until the chmod). The payload is content
hashes, not secrets, its siblings in .refdes/ are group-readable from
creation anyway, and _atomic_create already has exactly this property. The
name is unpredictable (16 hex chars).

Cleanup/portability: the existing finally still unlinks the temp on every
failure path; fdopen failure closes the raw fd (no leak); missing/read-only
directory raises OSError into the unchanged _record_seal_write refusal path.
Windows: os.open/O_EXCL work; the mode argument is advisory there, same as
the os.chmod line already in this function -- parity, not a new assumption.
