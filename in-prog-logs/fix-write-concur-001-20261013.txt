FINDING AND HISTORY

The report (in-prog-logs/current-main-rq01.tsv in the main checkout, row 16)
was verified against older main 8ff0cc8. Two commits between then and the
base already closed the original scenario: b7cc823 (#182, the rollback's
byte compare -- restore only while the lockfile still holds exactly the
bytes this writer wrote) and d804b59 (#195, the accept's read-stage-replace
and the rollback's read-compare-restore each inside project_write_lock).

The hole that survives on the base is the same race spelled with identical
bytes: two cooperating accepts of the SAME key stage the same lockfile text,
so the winner's own write is skipped as a no-op (edit.py, the
`staged != previous` guard), the winner's body lands, the loser's late
revision check conflicts, and its rollback -- seeing current == its own
staged bytes -- restores the pre-accept file. The winner's body, naming the
pin, is on disk with no pin: `refdes check` exits 1 with
`calc 'eff': source('analysis/budget.csv', 'eff') has no locked value`.

Reproduced deterministically at the base with

edit_mod._blocking_diagnostics to stand in for the winner's applied writes:
body landed, lockfile untouched):

    -p no:cacheprovider
Output at the base: B 409 conflict; body names the line: True; lockfile

WHY NOT A REORDER

The finding suggested moving the lockfile write inside the final
check-and-replace section. Rejected: the candidate gate resolves the new
source() line against the lockfile on disk (loader overlay covers item
source files only; build.py:1544 re-reads citations.yaml unconditionally in
run_calcs, and citations.verify reads it from disk too), so pins cannot
exist only in memory without threading a new in-memory overlay through
build and verify -- a design change §4 explicitly declines ("holding the
project lock across the gate would keep every other lock-taking writer out
of the project" for seconds).

THE FIX (src/refdes/serve/edit.py)

_LockfileWrite gains `watched`: the (canonical path, key) pairs this write
newly satisfies -- the diff of the pinned pairs across stage_source_pins
(which only ever adds; a changed source file is refused, not re-pinned),
minus the pairs the project's own bodies were already naming when the
accept read it. rollback, inside the same project_write_lock section and
after the byte compare, re-parses the tree read-only (loader.load_tree
write=False; no build, no lock taken) and skips the restore if any
source() line on disk now names a watched pair -- the tree moved under us
and the file has passed to a landed save. Unread additions stay §4's inert
pin and are still cleaned; pre-existing unpinned names (the never-fetched
project whose body already names rail_load -- test_a_rolled_back_accept_of_
a_never_fetched_project_leaves_no_lockfile) are excluded from `watched`,
so refusals' byte-for-byte restoration is unchanged.

Interleaving argument: any pin in `previous` survives every restore by
construction (adds excludes it), and any landed body naming a pair NOT in
previous must have been gated after some writer -- us or the winner --
wrote that pair, hence landed after the accept's `before` snapshot, so the
locked tree re-read at rollback sees it. The `watched` subtraction of
`named_before` cannot suppress a landed winner: a body naming an added
pair was gated over bytes written after the accept's snapshot, so the
snapshot cannot already name it.

GAPS LEFT OPEN (restated in the rollback's comment): the four #195 gaps
(read error, unacquirable lock, crash inside the one os.replace, a writer
that ignores the lock) plus: the loser's rollback runs before a
cooperating accept's own body write only if that accept failed to take the
project lock -- a non-cooperating writer, gap (4); and an OSError loser
whose rollback lands between the winner's lockfile write and its body
write is the same crash-window-shaped residue §4 documents.

PHASE 2 -- review fixes (F1, F2), 2026-10-15, Qwen3.8-Flash-Next

The independent review (in-prog-logs/fix-branch-review-20261014.txt in the
main checkout, and the reviewer's worktree
review-review-accept-pin-rollback-20261014) put the branch on HOLD with two
findings, both reproduced by event-driven probes in the reviewer's
.scratch/probe-accept-gate-window/:

F1 (HIGH): the winner-side window. The loser's rollback can run while the
winner is between its gate and its body replace -- the rollback's tree check
is a point-in-time read and cannot see a body that has not landed yet. End
state: winner's body on disk, its pin deleted, `refdes check` exit 1.

F2: `_accept_pins`'s `- named_before` exclusion dropped pairs the project
was already naming, unpinned, from `watched`, so the tree check never fired
for them and a loser's rollback erased a winner's adoption of exactly such
a pair.

Fixes, both in serve/edit.py:

F1: the final section of `_apply_locked` -- under the same lock that
replaces the body -- now calls `_reapply_pins`: if the lockfile no longer
holds what this accept staged, the pins are re-checked against the current
records (`locked_source_value`) and, when missing, re-staged through
`stage_source_pins` under fetch's own policy and written, all inside the
lock section that writes the body. `_Acceptance` carries the accept's
`plans`/`anchors`/`digests` for exactly this. A re-stage that fails is an
ordinary refusal (both files as found); `lock.previous` moves to the bytes
this write replaced, so the rollback of this apply owns what it should.

F2: the exclusion is gone. `watched` is now every pair this write newly
pins, and the check compares the *naming lines*: `_accept_pins` snapshots
the sorted `(item key/id, line)` multiset of the snapshot's uses of the
watched pairs (`referents`), and `_pins_referents_moved` re-parses the tree
under the rollback's lock and restores only while disk names the watched
pairs with exactly those lines. A second line over a pre-named pair -- an
adoption -- moves the multiset. A snapshot whose uses cannot be walked for
non-OSError reasons records `referents = None` and the rollback declines
(the reviewer's F4 note; inert pin, documented residue). The reviewer's F3
(latency of a tree parse under the lock on the refusal path) is accepted
and documented, not designed around.
