### 3. What I changed

One shared sentence, so there is still only one phrasing (run-3 N2):

- `model.py` — `READ_ONLY_REFUSAL` / `read_only_refusal(consequence="")`, the
  stem plus what the refused write was for. Both existing spellings
  (`schema_json.write_schema`, `revise._refuse_unwritable`) now call it and
  produce **byte-identical** text to before (`read_only_refusal()` with no
  argument is exactly the old string).
- `seal.py` — `save_seals` returns `bool`; an `OSError` becomes an **error**
  diagnostic naming the file and saying the entries are `NOT sealed`. Error,
  not warning: `build` is the command that seals, and an unsealed entry has no
  append-only protection at all (`refdes check --help` says so).
- `boards.py` — `save_manifest` same shape, same severity, naming
  `.refdes/boards.yaml`.
- `lifecycle.py` — new `BaselineUnwritable(OSError)` carrying the display path,
  raised by `_save_baseline_file`. Three callers, three shapes:
  - `stamp()` → new `StampOutcome(status="unwritable", refusal=<rel>)`;
  - `migrate_hash_format()` → warning + keeps its report (the comparison it
    feeds is computed in memory and is still correct; this is what took `audit`
    down);
  - `revise`/`calc-rewrite`/`standard upgrade` → propagate unchanged, which is
    the existing `test_an_explicit_write_still_raises_on_a_read_only_tree`
    contract.
- `cli.py` — `_run_stamp` turns `unwritable` into a one-line `error: cannot
  write <file> (read-only tree?) -- <kind> '<name>' was not stamped…` and exit
  **2**; `cmd_build` wraps `render_site` and refuses with `error: cannot write
  the site to <dir> …`, exit **2**, printing the diagnostics gathered first.

Exit-code choices, against `docs/cli-reference.md`:

- `build` on a refused seal / manifest → **1** (`errors found`): it is reported
  through the ordinary `ERROR <file> — …` diagnostic channel, and the table says
  that channel only gets `1`.
- `build` on an unwritable site dir, `revision`/`release` on an unwritable
  baseline → **2** (`configuration error`, the same code the `--no-write`
  refusal uses): nothing is wrong with the project, the command refused to do
  the thing it was asked to do. Needs a table row — done.

`--no-write` is unchanged and pinned by a new test: it never reaches the write.

### 10. Review of PR #132 (finding 1): `revise` reported a seal update that
###     never happened

The reviewer was right about the mechanism. I had made `save_seals` return a
bool instead of raising, and `revise._carry_forward_seals` ignored the return
and appended the board to `updated` regardless — so a seal file the filesystem
refused was reported as carried forward. My own `save_seals` docstring and the
PR body both claimed `revise` "gets the same tolerance"; both were wrong.

One correction to the review's prediction, since it changes what the test has
to assert. The predicted symptom was a quiet false success. What actually
happened on my branch was a *different* traceback, from `revise.py:899`
(`_restore_seal_files`) via `_rollback` — reproduced at `.scratch/rvbug/probe.py`
against both trees:

| | main | this branch, pre-fix |
|---|---|---|
| where it died | `save_seals` (raised) | `_restore_seal_files` (in rollback) |
| tree left behind | item renamed, seal stale | item renamed, seal stale |

So it was still a raw traceback, just from a second site, and the tree was
still left half-rewritten. The defect is the same one the reviewer identified
— the ignored return — and it is now fixed at the source rather than papered
over.

**Fixes (`src/refdes/revise.py`, `src/refdes/calc_rewrite.py`):**

- New `revise.Refused`, carrying one message. Both carry-forwards raise it
  instead of continuing: `_carry_forward_seals` checks `save_seals`'s return
  before touching `updated`, and `_rewrite_baseline_file` translates
  `lifecycle.BaselineUnwritable` into the same shape.
- `apply()` and `calc_rewrite.apply()` catch it, **roll the whole transaction
  back**, and return `ok=False` with the message — so no board is ever claimed
  as carried forward and the project is not left renamed with stale seals.
- `_restore_seal_files` now compares before writing. This is what made the
  rollback itself crash: it rewrote a file this run had not changed, which is
  a second refused write in the same run. A rollback exists because something
  changed; a file that did not change is already correct on disk.

**Verified against the reviewer's scenario** (items/ writable, `.refdes/`
read-only, a sealed entry whose hash `revise` carries):

```
$ refdes revise mapping.yaml
refused:
  cannot write .refdes/log-seal.yaml (read-only tree?) -- the renamed entries' seals were not carried forward, and the next build would report every one of them as modified since it was sealed. Make the tree writable and run it again.
  rolled back.
[exit 1]
```

And the tree afterwards is untouched: `summary:` still `summary:`, the schema
overlay un-bumped, the seal file byte-identical, and `refdes check` still clean
with no `seal_violations`.
