2. ROOT CAUSE (proven with evidence, NOT the timeout)
=====================================================================
Rejected: cold-start starvation / interpreter startup under load. A cold
start to token-file-written measures ~0.5s on this box
(.scratch/flake-repro/time_cold.py: 0.557s / 0.508s / 0.470s). Burning even
the old 60s budget needs a >100x slowdown; the 180s budget raised it to >350x
-- implausible with 20 cores, and the prior timeout raise (905ce6b) did not
stop the flake, which is itself evidence against it.

The real chain, proven by two bounded experiments (.scratch/flake-repro/):

  exp1_time_wait_refusal.py (deterministic, REPRODUCED):
    launch serve --port P --token-file tf; wait tf; open one HTTP connection;
    SIGKILL serve; close the client so serve's accepted socket finishes its
    close (TIME_WAIT sits on 127.0.0.1:P). Then:
      - a plain bind of 127.0.0.1:P (no SO_REUSEADDR) -> EADDRINUSE
      - a real `refdes serve --port P --token-file tf` child -> exit 2,
        stderr "error: cannot listen on 127.0.0.1:P: Address already in use
        -- ...a launch that stopped a moment ago still has sockets closing
        on it..." (that exact wording is the product's own, server.py:289-293)
      - tf NEVER rewritten -> _wait_for_file(differs_from=stale) would spin
        its entire 180s budget against a dead child and then fail.
    That matches the reported failure exactly ("waits for the token file and
    gives up", passes when re-run alone -- by then the socket is long gone).

  exp2_steal_realism.py (why ~6 concurrent suites is the trigger):
    Vector A: the kernel hands a released ephemeral port BACK to bind(0)
    after ~7,500 allocations (measured: re-offered after 7,510 probes in
    0.04s of churn). free_port()'s whole design picks from the ephemeral
    range (this box: 32768-60999) -- so seconds after the test SIGKILLs the
    first launch and frees P, ambient bind(0)/connect traffic (concurrent
    suites, browsers, IDE servers -- `ss -s` shows hundreds of live TCP
    sockets, and vmstat showed >200k context switches/s even "idle") can
    hand P to someone else: another suite's free_port() may pin P with its
    own serve --port and HOLD it for its whole test (seconds), or a
    loopback connection may hold P in TIME_WAIT for ~60s. Either way the
    relaunch's bind fails exactly as in exp1, while a machine running this
    suite ALONE almost never advances the allocator the ~7.5k allocations
    needed within the sub-second relaunch window -- flake, not break.

  Corroboration from the repo itself:
    - Only test combining a pinned --port with a --token-file wait is THIS
      one -- and it is the only named flake. Port-only tests fail loudly
      (exit 2 asserted by their own tests); token-only tests use ephemeral
      ports and never rebind.
    - in-prog-logs/review-followups-2026-10-11.txt:193-200 documented this
      exact second mechanism ("another concurrent suite's free_port() could
      steal the now-free port; serve then exits 2 and the token file stays
      stale forever -- ... which no wait-budget change would fix") but chose
      to raise the timeout instead. The raise shipped; the flake remained.

Why it is slow when it fires: _wait_for_file never checks whether the child
is dead, so the failure burns the whole deadline (was 60s, now 180s) before
the assertion runs -- "every worker and reviewer had to work around it".

3. FIX PLAN (step 3)
=====================================================================
a) tests/serve_support.py free_port(): stop pinning ports the OS will
   re-hand to other processes -- choose a random, probe-bindable port
   BELOW ip_local_port_range (read from /proc when available), which the
   allocator never auto-assigns to anyone. Same helper shape, shared fix
   for every --port test.
b) tests/test_serve_cli.py _wait_for_file(): take the launched process and
   return as soon as readiness holds; if the child exits first, fail
   immediately with its exit code + stderr tail instead of burning the
   deadline -- the real readiness condition is "file rewritten", but only
   while the waiter's premise (the child is alive) can still produce it.
c) PRODUCT (real bug, real users): _Server.allow_reuse_address = False
   turns any still-closing old socket on the pinned --port into a
   60-second-restart wedge (exp1: the product's OWN error text describes
   it). SO_REUSEADDR (the stdlib HTTPServer default!) makes a relaunch on
   your own port succeed while old sockets close, and on POSIX it does NOT
   let a live listener be shared/stolen -- the busy-port refusal stays.
   On Windows SO_REUSEADDR means bind-over-anyone (a hijack), so there it
   stays False. New subprocess test pins the fixed behavior (crash with an
   open connection -> relaunch on same --port succeeds and rewrites tf).
d) Before/after proof: loop the flaking test 20x while 6 concurrent churner
   suites hammer free_port()/--port, before and after.

5. THE FIX
=====================================================================
a) PRODUCT src/refdes/serve/server.py:
   _Server.allow_reuse_address = os.name != "nt" (was False everywhere).
   POSIX SO_REUSEADDR only reclaims a port whose old sockets are closing --
   a live holder still answers bind with EADDRINUSE (proven: the busy-port
   refusal tests, test_serve_cli.py and test_serve_security.py, pass
   unchanged). On Windows SO_REUSEADDR means bind-over-anyone, so the
   strictness stays and the "launch that stopped a moment ago still has
   sockets closing on it" hint in _bind_failure_message is now Windows-only
   wording (POSIX: "something else holds it"). This is the real-user fix:
   the crash-and-restart-on-your-own-port wedge is gone, and it is what
   turned the stolen port into a 60-second dead end in the test.
   Fragment: changelog.d/serve-relaunch-reclaims-own-port.fixed.md
   (rule: user-visible behavior change -> fragment; category `fixed`).
b) TEST HELPER tests/serve_support.py free_port(): a random probe-bindable
   port BELOW ip_local_port_range (read from /proc, IANA 49152 fallback),
   so the OS allocator -- which re-hands released ephemeral ports after a
   few thousand allocations (measured ~7.5k) -- can never point a
   concurrent process at a test's pinned port, neither via bind(0) nor via
   a connection source port. Shared fix: every --port test in
   test_serve_cli.py/test_serve_security.py goes through this helper.
   New test_free_port_hands_out_nothing_the_os_will_later_reassign pins
   the contract.
c) TEST HELPER _wait_for_file(..., proc=): the wait now ends the moment the
   launched child is dead, failing immediately with the exit code and the
   first three stderr lines -- the real readiness condition is "file
   rewritten", and a child that exited cannot write it. Kills the
   60s/180s-deadline burn that made this flake cost everybody a three-
   minute stall. New test_a_wait_on_a_dead_launch_fails_at_once_naming_the_exit.
   The deadline itself stays generous (180s) for true slow starts -- a
   healthy child is ready in ~0.5-1.5s and the wait returns immediately.

Sabotage (COMMON rule):
  - (a): allow_reuse_address flipped back to False -> the new restart test
    FAILED 1.28s with the exact stale-token-file symptom -> restored ->
    10/10 + 15/15. (This doubles as the fails-before record.)
  - (b): free_port reverted to bind(0) shape ->
    test_free_port_hands_out_nothing_the_os_will_later_reassign FAILED in
    0.08s (port inside the ephemeral range) -> restored -> passes.
  - (c) was not sabotaged on purpose: its failure mode IS a 120s burn
    (that is the bug), which the other two sabotages plus the 1.28s
    pre-fix failure of (a) already demonstrate at real-test level.
