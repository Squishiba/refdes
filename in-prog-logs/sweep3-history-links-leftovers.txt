K4 (#184) on_change as a link-verb name — INVESTIGATED, no code change
------------------------------------------------------------------------
The collision is ALREADY a load-time rejection with a clear message:
schema.py _reject_reserved_link_verb (lines 131-147), wired into
link_types loading at schema.py:750/752, rejects any link verb (or
inverse) whose name is in parse.RESERVED or parse.OVERRIDABLE — and
OVERRIDABLE includes on_change. It landed in 052d0c3 ("feat(vocabulary):
on_change mode log -> timeline (P9); reserved-name link verbs are load
errors (#184) (#196)"), an ancestor of this branch's main.

Live verification (scratch project .scratch/k4-onchange/proj, hardware@3
via `refdes init`; refdes-schema.yaml declares
link_types.on_change with an inverse; items/a.yaml uses the key):

  $ refdes check          (exit 2)
  configuration error: link_types.on_change: the link verb 'on_change'
  collides with the engine's reserved front-matter key 'on_change' --
  items spell on_change: for the engine's own reading, so this verb
  could never be written on an item; rename the verb

  $ refdes schema         (exit 2, no JSON emitted)
  configuration error: <same message as above>

So the review's symptom ("an error, and the link is lost") can no
longer happen silently: the project refuses to load at all, the verb
is named, and the remedy ("rename the verb") is in the message.

Options for Jared (per the task; NOT implemented):
  (a) reject `on_change` as a link-verb name at schema load with a
      clear message — THIS IS WHAT THE CODE DOES TODAY (and for the
      whole reserved/OVERRIDABLE class plus inverses, read from
      parse.py's own sets so future reserved keys are guarded for
      free).
  (b) let link verbs own the name, as fields can (parse.py:981 already
      lets a declared field take over an OVERRIDABLE key) — this would
      need front matter to disambiguate `on_change:` by the type's
      declaration, which is exactly the guessing the engine refuses;
      the schema-load error exists because the two readings are
      textually indistinguishable.
  (c) leave it — moot if (a) is accepted as already done.
  Recommendation: (a) = accept the current behavior as the fix for
  #184 and close the review item; (b) is worse by parse.py's own
  design (front matter spells OVERRIDABLE keys for the engine). No
  code change made.
