## Old-spelling posture (matches P2's hard error, gated by standard pin)

- P2 precedent = hard error naming the new spelling (project key + item key),
  item-level errors but still applies the override.
- Gate: the rename belongs to hardware@3. `standard_version` (model.Project) is
  set iff the project pins a bundled base with an integer version.
  - pin >= 3 or no pin: `log` is a hard error "…was renamed to…timeline…" at
    (a) project setting on_change.default, (b) type/field/body annotations,
    (c) item front-matter overrides (error + still applied as `timeline`,
    exactly P2's item-level posture).
  - pin 1/2: released standards carry `log` in their own yaml; those pins keep
    loading unchanged. Annotations keep the spelling `log` internally (audit/
    vocabulary output stays faithful); item overrides are normalised to the
    canonical `timeline` internally (behaviour-identical) so every downstream
    consumer keeps reading one canonical vocabulary.
- Canonical modes become (invalidate, timeline, ignore). Downstream consumers
  only ever compare against INVALIDATE (build.py, cli.py) or read
  FieldSpec.on_change back out (render/audit/vocabulary), so keeping `log` in
  FieldSpec under pre-v3 pins cannot change behaviour. Verified by grep
  (src/refdes/{build,cli,model,schema_json}.py) — membership checks are only
  on author-supplied *override* values (parse/model) and config validation.
